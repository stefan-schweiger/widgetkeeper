# Widgetkeeper — notes for Claude

Homey Pro app (`com.thomassidor.widgetkeeper`) of custom dashboard widgets. Never rename a widget id: it breaks widgets already on dashboards. 1.0.0 renamed Price Badge, Thermostat Shortcuts, Sensor Dots and Flow Variables to Energy Price Strip, Thermostat Presets, Activity Dots and Variables; the 0.9.0 changelog and posts keep the old names, and README.md their old anchors (`<a name>`). The electricity design spec is `temp/Homey electricity dashboard widget.zip` (`temp/` is gitignored).

## Commands
- Use the **project-local Homey CLI v4**: `npx homey …` (the global `homey` is an old 3.7.x).
- `npx homey app validate --level debug`: compiles the TS and validates.
- `npm test`: vitest in `test/` (`npm run test:watch`), run in Europe/Copenhagen. Service tests mock `homey-api` with `test/helpers/fakeHomey.ts`; widget tests run the unchanged `public/widget.js` in happy-dom (`test/helpers/loadWidget.ts`). CI (`.github/workflows/ci.yml`): typecheck, tests, validate.
- `npm run typecheck` (with `--noUnusedLocals`: an unused import, local or private member fails): `tsc` for the app plus a non-strict `checkJs` pass over every `widgets/*/public/*.js` (`tsconfig.widgets.json`, which sets `strict: false` explicitly since TypeScript 7 defaults to strict; the window globals are in `types/widgets.d.ts`).
- `npm run diagnostics`: see Diagnostics.
- `npx homey app install`: builds and installs on the active Homey (firmware 13.x). `npx homey app run` (live logs, hot reload) needs Docker Desktop, which usually isn't running.
- `npm run test-dashboards [-- lights media]` (`--remove` takes them away): one web dashboard per widget type on the active Homey (`Test · <widget>`, id `test-<type>`), each widget titled by what it tests, plus a deleted device/flow/variable and an empty one where it applies. Re-running replaces those and keeps the user's own. It picks devices, flows and variables by capability and class (never by name) through the widgets' own autocompletes, and writes the app setting `webDashboards` directly (the `/web/…` API also wants the password's session). Flow Buttons only gets flows that don't look like security, alarm or lock flows: a tap starts them for real.
  - It logs in once through the CLI's own code (`homey/lib/api/ApiCommandRuntime.mjs`). Every `homey api raw` logs in through Athom's cloud, and ~30 in a row got `Too many requests` for over half an hour (2026-10-11). `HOMEY_TOKEN` (a personal API key) with `HOMEY_ADDRESS` (`http://<ip>`) skips the cloud.
- `npm run web-socket`: bundles `socket.io-client` v2 (MIT; what Homey's realtime speaks) into the committed `settings/socket.io.js` with esbuild; a test checks it's the installed version. Not `homey-api`'s browser build: its licence is proprietary.
- `npm run flow-icons`: see `.claude/rules/widgets/flows.md`.
- Renders (details in `.claude/rules/renders.md`; read it before running or changing one) run headless Edge through `scripts/headless.mjs` and show made-up data on a fixed clock: **never put real device names or readings in them.** Every render is byte-identical between runs, except the live electricity chart's antialiasing.
  - `npm run app-images`: the three App Store PNGs in `assets/images/` from the widget previews (`dev/app-images.json`).
  - `npm run previews [-- qa-dark …]`: the widget preview PNGs from `dev/widget-previews.html` and the README's `docs/previews/`. A new widget needs an entry in `scripts/render-previews.mjs`'s frame-id map.
  - `npm run screenshots [-- thermostat …]`: `docs/screenshots/*.png` from `dev/screenshots.html` (the real widgets, Homey's dark mode, 358 px at 3x).
  - `npm run clips [-- lights stack]`: the README's animated WebP clips `docs/clips/<id>.webp` from `dev/clips.html`.
  - `npm run showcase [-- home energy …]`: `docs/showcase/<id>.png`, dashboards of real widgets on a drawn tablet (`dev/showcase.html`, the made-up house "Solbakken").
  - `npm run web-showcase [-- dashboard front editor]`: `docs/web/<view>.png`, the web dashboards page in a drawn browser.
- Dev previews: serve the repo root (`python -m http.server 8765`) and open `dev/<id>-preview.html` (the Electricity Overview's is `dev/preview.html`): mock data, usually dark, light and 300 px cards and a simulated Homey; `?lang=de` for a language (`dev/i18n.js`). They share `dev/preview.css` and `dev/mock-util.js` (load it before `mock-electricity.js`, `mock-weather.js`, `mock-heatmap.js` or `showcase-data.js`).
  - Real data: `preview.html?snap=/temp/real-snapshot.json` (`#live=0.4` / `#price=0.3` simulates a scrub), `weather-preview.html?snap=/temp/met-compact.json` (a MET response), `heatmap-preview.html?snap=/temp/heatmap-lux.json` (from `npm run diagnostics -- --json --heatmap <deviceId>:<capabilityId>`; also `?today=&hour=`).
  - `?open=<id>` opens a dot's or tile's panel (sensordots, lights); `stack-preview.html?act=unlock|timer|flow` presses one 1.5 s in, for a headless screenshot; `media-preview.html` needs `temp/screenshot-icons.js` (from `npm run screenshots`); `cameras-preview.html` uses drawn scenes, so no real camera images go in the repo; `textline-preview.html` has no Google Fonts (the user wants fonts hosted locally only).
  - Headless screenshots: `msedge --headless=new --screenshot=… --user-data-dir=<fresh dir>` (a fresh profile avoids a stale cached CSS).

## Architecture
- TypeScript, ESM (`"type": "module"`), compiled by `tsc` to `.homeybuild/`; relative imports need `.js` extensions. `app.ts` owns the services (`lib/*Service.ts`). They use `homey-api`'s `HomeyAPI.createAppAPI` (needs the `homey:manager:api` permission; the shared instance is in `lib/appApi.ts`).
- Widget front ends (`widgets/<id>/public/`) are **plain JS** with no build step: Homey serves them as-is. Every widget is three files:
  - `widget.js`: `create<X>Widget(root, opts)`, the UI. Each is an IIFE, so several share one page (the Smart Stack).
  - `mount.js`: `mount<X>Widget(Homey, {root, frame})`: the settings, `Homey.api` calls, realtime and `ready`/`setHeight` (measured on `frame`; `.frameClass` is the body's classes). The Smart Stack calls the same mounts with a slide and a Homey of its own, so keep a widget's wiring here: nothing on `document.body`, no `getElementById`. `test/widget-mount.test.ts` mounts each into a plain element with a failing Homey.
  - `index.html`: loads the kit first, then only runs `WidgetkeeperKit.undoTextZoom()` and calls the mount with the frame's Homey and `document.body`.
  - **The kit** (`widgets/spacer/public/kit.js`, `window.WidgetkeeperKit`; Homey serves each widget's folder and has no shared one, so it lives in the Spacer's): what the widgets used to copy. `undoTextZoom()`, `el()` (with `ns` for SVG), `setMask(node, url, var)`, `tileNames()`, `withName()`, `formatSince()`, `baseTitle()`, `lowestSlot()`, `loadMarks()`, `wireTileNames(Homey, setNames)`, Flow Buttons' `icons`, a capability value's `scaled()`/`formatNumber()`/`formatValue()` (`TIGHT_UNITS`), and the colours' `COLORS`, `colorStyle()` and `applyColors()` (see Widget styling), with their stylesheet `kit.css`. Every index.html loads `../spacer/kit.js` first and `../spacer/kit.css` before its other stylesheets (a test checks both), the dev pages `../widgets/spacer/public/kit.js`, the web dashboards page too; the stack's pages use the stack's; the tests load it before a widget (`KIT` in `test/helpers/loadWidget.ts`, not in `DEPS`). `test/widget-html.test.ts` checks no widget keeps a copy. Loading files across widget folders isn't tried in the phone apps yet (Charts, Variable Presets and the Smart Stack relied on it before the kit): check once on a phone.
- Shared back-end helpers (tested in `test/shared-service.test.ts`):
  - `lib/DeviceTracker.ts`: lazy per-device tracking for the Light, Curtain, Lock, Media, Quick Action, Room Health, Sensor Alarm, Value and Thermostat services. Tracks on the first `/state`, re-reads with `$cache: false` on later ones (`readFresh()`: re-reads of one device at the same time share one `getDevice`, across every tracker and Cameras' `/state`; homey-api itself only shares `$cache: true` calls), re-tracks when `signature()` changes. A failed re-read disposes and throws, unless it failed for a passing reason (`isTransientError()`: 408, 429, 5xx, timeouts, connection errors), which keeps the entry, so a crowded dashboard's load burst doesn't show devices as missing. An entry is disposed once; a track still under way at `stop()` throws instead of subscribing; dropped after 10 min idle. `each()` is the multi-device `getState` loop with `{id, missing: true}`; also `readZones()` (one read shared for 60 s; a failed read gives the last zones read, so rooms don't split) and `zoneRef()`.
  - `lib/capabilities.ts`: `describeCapability()` (an empty title falls back to the id, empty units are null), `presentCaps()`, `readCaps()`.
  - `lib/autocomplete.ts`: `matches`, `withNone`, `listDevicesWhere`, `listCapabilitySlots`, `AutocompleteItem`, `devicesAndZones()` (every device and zone, one read shared for 5 s: the autocompletes ask on every keystroke; the web editor's pickers and Media's speaker list use it too).
  - `lib/sharedCache.ts`: a read shared while it's at most `maxAge` old (flows, Flow cards, dashboards, Moods).
  - `lib/widgetApi.ts`: `logPerf`, `idList`, `logged`, `keyResult` for the widgets' `api.ts` handlers.
  - `lib/widgetAutocompletes.ts`: every widget's autocomplete listener in one table (`widgetAutocompletes(app)`); `app.ts` registers them with Homey and the web dashboards' editor calls the same ones. A test checks it matches the manifests.
  - `lib/widgetRoutes.ts`: `findWidgetRoute()`/`callWidgetRoute()` (a widget's own API route from the manifest, for the Smart Stack's `/call` and the web dashboards' `/web/call`) and `routeKeyUse()` (the routes that act with the stored personal API key).
  - `lib/deviceIcon.ts`: device icons (see `.claude/rules/widgets/thermostat.md`; `libraryIconUrl()` and `driverIconPath()` are where one is, for the widgets and the web editor alike), `homeyUrl()`, `fetchImageBase64()`, `deviceImage()` (camera snapshots, album art).
- **The usual device widget** (the widget notes only say where they differ): a `devices` setting (`singular: false`, read with `Homey.getDeviceIds()`); `GET /state?deviceIds=a,b`, one entry per id in order (`{id, missing: true}` for a deleted device), through `DeviceTracker`, so renames, changed capabilities (re-tracked) and deleted devices show on the next `/state` (an open widget used to keep its first read forever); realtime `<id>:state {deviceId, capabilityId, value}` from one capability instance per capability; tracking dropped after 10 min without `/state`, and the widget refetches every 5 min; a failed refresh keeps the tiles with a transient message (only a failed first load replaces them with the error); optimistic values for 10 s.
- **Taps** (`onTap()`, born in Quick Actions): a touch that ends within 10 px of where it started, with `click` kept for mouse and keyboard; a drag is left alone, so the dashboard still scrolls. It works on Android, where the dashboard takes drags (see the Electricity Overview).

## Widget styling
Homey's guide: https://apps.developer.homey.app/the-basics/widgets/styling. Homey injects its stylesheet into every widget frame; outside Homey (the dev previews and renders) none of its tokens is defined.
- **Frame:** `body.homey-widget` (16 px padding), `.homey-widget-small` (8) or `.homey-widget-full` (0; the transparent widgets use it). `.homey-dark-mode` is set on the frame in dark mode, about 1 s in, by the SDK.
- **Spacing:** `--homey-su` = 4 px; `--homey-su-1` … `--homey-su-8` = 4 … 32 px.
- **Type:** `--homey-font-size-small/default/large/xlarge/xxlarge` = 14/17/20/24/32 px with `--homey-line-height-*` = 20/24/28/32/40 px; `--homey-font-weight-regular/medium/bold` = 400/500/700. Natively only 14 regular, 17 any weight, 20 medium and 24/32 bold are used. The classes `.homey-text-bold/medium/regular/small/small-light` and `.homey-text-align-left/center/right` have no documented sizes, so the widgets set the variables themselves.
- **Colours:** text `--homey-text-color`, `-light` (less important or disabled), `-white`, `-blue/green/orange/red`, `-highlight/success/warning/danger`; `--homey-background-color`; the palette `--homey-color-mono-000…1000`, `--homey-color-blue/green/red-050…900`, `--homey-color-orange-500`; semantic `--homey-color-white/blue/green/orange/red/highlight/success/warning/danger`. `transparent` in `widget.compose.json` makes a see-through widget.
- **Lines, radius, icons:** `--homey-line-color(-light)` and `--homey-line(-light)` (`1px solid` that colour), `.homey-border(-top/right/bottom/left)`; `--homey-border-radius-small/default` (no documented values; our fallbacks are 3 and 14 px, Homey's are 5 and 10 px); icons are an SVG `mask-image` with `--homey-icon-color-dark/light/white/blue/green/orange/red` and `--homey-icon-size-small/regular/medium` = 14/16/20 px; tables `.homey-table(-striped)`.

How this project uses it:
- Every widget defines its own aliases on its root (`--ew-*`, `--tw-*`, `--qa-*` …; not `:root`, so the previews' light-mode overrides inherit), each a Homey token with the spec's dark-theme px or hex as fallback. A 4 px step uses `--homey-su-N` (a mixed padding like `8px 10px` stays px), a 20 px icon `--homey-icon-size-medium`, a 1 px line `--homey-line(-light)`. The font is set on `html`, so Homey's own on `body` wins. The settings page uses Homey's settings classes (`homey-header`, `homey-form-*`, `homey-button-*`).
- Deliberate exceptions, measured or chosen, noted per widget: the 12/16 label size (no token); the native-tile 10 px radius and dark tile fills (`#181920`, `#2B2C36`, `#2E3039`); Sensor Alarms' 14/18 text and the thermostat's 12/16 button text; the alarm and temperature colour pairs (picked to pass 4.5:1).
- Homey's real token values, read from the Homey's `/widgets/css/_homey-variables.css` (imported by `homey.widgets.css`, 2026-10-18), differ from many of our fallbacks, so the dev previews and renders don't look exactly as on the Homey: `--homey-color-red` `#D81C1D` (red-500, both modes; ours `#F25F5C`), `-green` `#3FC700` (ours `#71D51B`), `-orange` `#FF8400` (ours `#F07A1F`), `-blue` `#0082FA` light and `#339BFB` dark (blue-400; ours `#2F8DF6`); dark text `#E4E4E7` (mono-900), muted `#999AA3`, the dark background `#1F2029`; `mono-100` is `#2B2C36` (Sensor Alarms' tile). The shades used by Deep: blue-600 `#0068C8`, blue-700 `#004E96`, red-600 `#AD1617`, green-700 `#267700`. `dev/schemes-preview.html?tokens=homey` sets them. The fallbacks stay (the user, 2026-10-18: Default must look as before).
- **Colour style** (`colorStyle`, "Colour style", called "Colours" until the user renamed it the same day: `soft` "Default" or `deep` "Deep"; the user's choice of four directions, 2026-10-18, mocked up in `temp/color-scheme-directions.html`, then a second round the same day): every widget with a state colour but Weather (Deep is one of its `theme`s), Clock, Cameras, Spacer and the Smart Stack. Default is the calmer look, Deep the stronger one. `kit.css` defines every colour in two sets, always: bright (`--wk-<name>-bright`, Homey's tokens, the old fallbacks) and shade (`--wk-<name>-shade`: blue-600, red-600, green-700, orange `#A85700`, purple `#7500FB`; yellow stays, as no dark yellow reads as yellow; 5.2–7.2:1 with white text), each with the text on it (`--wk-on-<name>-<set>`), on `.wk` (each widget root, set by the kit's `applyColors(root, {style, color, fallback})`, not `:root`, so the dark tokens resolve). `--wk-<name>` is the scheme's pick for tinted tiles: bright in Default (mixed 22 % into the tile, as before), the shade in Deep (`.wk.wk-deep`, a solid fill with `--wk-on` text). `data-wk-color` (a `color` setting) gives `--wk-c`/`--wk-on` and both sets (`--wk-c-bright`, `--wk-c-shade` …). Two kinds of widget: **tinted** (Quick Actions, Sensor Alarms, Locks, Device Values, Lights, Curtains, Notes, Timers, Flow Buttons, Variables, Price: Default byte-identical to before; Deep solid shades) and **already solid**, whose small parts were full colour (Thermostat and Variable Presets' lit button, Heatmap, Media, Activity Dots): these were swapped at the user's request (round 2), so Default uses the shades and Deep the bright colours, and their Default changed. Days Since's Default was toned down (only the bar shows the level, at 50 %) and Room Health's rings are mixed 60 % into the track in Default, full in Deep. Electricity and Charts put `wk` on the root (their render test compares the markup inside it) and only strengthen the areas in Deep. Each widget's rules are in its own CSS, described in its note. `colorStyle()` reads Device Values' old `bright` (never released) as Deep. The fixed blues of Quick Actions, Variables, Curtains, Media and Timers became a `color` setting (Heatmap's, before Colours). `dev/schemes-preview.html` shows Default | Deep | Deep with another colour for every one (`?mode=light`); `test/color-scheme.test.ts` checks the settings, kit.css's sets, the mounts and that each CSS has Deep rules.
- Not switched, because switching could change the look: `--homey-text-color-danger` for errors (we use `--homey-color-red`), `--homey-icon-color-*` (we use the text or muted colour), `--homey-border-radius-small` for the 3 px heatmap cells, the `.homey-text-*` classes.
- Most shared front-end helpers are in the kit (see Architecture). The copies left are checked equal by `test/widget-html.test.ts` ('copied widget helpers'): `perfParam()` (every mount.js), `nameKeys()`, `onTap()` (every copy records every `touchend`, not only taps, so the click a browser still sends after a short swipe is ignored; Lights = Curtains, with a `stop` option for a control inside the tile; Flows = Activity Dots = Room Health; Timers = Locks = Days Since; Media's and Variables' have no keydown on purpose; the stack's is its own), `wireBar()`, the dark frame block of Thermostat/Heatmap/Media/Weather and the tile/frame rim. A copy that differs on purpose is left out with a comment there.
- Checking a styling change: `npm run screenshots` before and after. Every image should be byte-identical (the clock is fixed).

## Widget settings
- Widget settings are one flat list: the phone app (Android 10.1.1's code, 2026-10-08) draws exactly `text`, `textarea`, `number`, `checkbox`, `dropdown` and `autocomplete`, each a row with its value; there's no heading or group type (an unknown type becomes a row that opens a text field). So per-tile settings are grouped by their titles: the first of each group flush left (`Button 1: flow`, `Timer 1: minutes`), the rest indented with two em spaces (U+2003) and a dash (`  – Colour`, `  – Name`). A `━━ ` rule before the first row (tried 2026-10-08) indented it past the `–` rows on iOS. Numbered titles (`Tile 4`) put a non-breaking space (U+00A0) before the number: iOS showed `Tile 4` as `Tile` (2026-10-09). The web dashboards' editor reads its cards from this convention (`settingSections()`, from the English titles), so keep it in a new setting; a test checks every language groups alike.
- Widgets placed before a setting existed don't have it, so the mount reads a missing value as the default: `settings.x !== false` for a checkbox that's on by default, the default for a dropdown. A setting removed from the manifest never reaches the phone's `getSettings()` again (see Homey API facts).
- An autocomplete listener gets the other settings but not the `devices` selection, so a widget whose other autocompletes depend on the device (Thermostat Presets, Insights Heatmap, Media) picks it with a `device` autocomplete and reads `settings.device.id`.

## Personal API key
- The app's token lacks `homey.logic` (Variables, Variable Presets), `homey.flow.start` and `homey.flow` (Flow Buttons, Media's buttons), `homey.mood.set` (Room's Moods) and `homey.dashboard.readonly` (Smart Stack). Diagnostics list its scopes (`apiScopes`, from `sessions.getSessionMe()`).
- So the user makes a personal API key (Homey web app → Settings → API Keys) and pastes it on the app settings page. `lib/PersonalApiKey.ts` (one instance, `PersonalApiKey.for(homey)`, as `app.apiKey`) keeps it in the app setting `variablesApiKey` (the name predates Flow Buttons), never sent back or logged. `save()` checks it (`HomeyAPI.createLocalAPI({address: homey.api.getLocalUrl(), token})`, then `getSessionMe()`) and answers `{ok, variables, flows, dashboards, moods}` (what it may do, `USES`; the settings page says so; a key that may do none is refused) or `{ok: false, reason}`. `run(fn)` turns `Missing Scopes` into `keyScope` and a 401 into `keyInvalid`. App API: `GET/PUT /variables-key` (`{set}`, `{key}`). Without a usable key the routes answer `{ok: false, reason: 'noKey' | 'keyScope' | 'keyInvalid'}` and the widgets show that message (`KEY_PROBLEMS`).
- Which permissions (README *API key*; the settings page lists them, `varFor*`/`varTick*`): Homey's API Keys page (`my.homey.app`, read from its bundle 2026-10-15) offers the groups Homey (`homey`, everything), Devices, Flows (View Flows, Start Flows), Moods (View, Set), Variables (View), Zones, Notifications, Apps (View, Control), Users, Logs, Alarms, Presence, System, Updates and Location; a group's box includes those under it. **There's no dashboards box**, so `homey.dashboard.readonly` only comes with Homey (everything). From homey-api's specification (`HomeyAPIV3Local.json`): `updateVariable` → `homey.logic` (Variables), `triggerFlow`/`triggerAdvancedFlow` → `homey.flow.start` (Start Flows), `runFlowCardAction` → `homey.flow` (Flows), `setMood` → `homey.mood.set` (Set Moods), `getDashboards` → `homey.dashboard.readonly` (Homey). Homey's own labels in all 13 languages are in each `my.homey.app/assets/<lang>-*.js` chunk (`scopes:{…}`); the strings quote them.
- The web dashboards' browser key: which scope an app's own API (`/api/app/<appId>/…`) and the realtime `subscribe` take isn't documented ("the requesting user needs permission to your app") or in the specification, and isn't tested with a narrower key; a full-access key works. Testing it needs a key made for it (`POST /api/manager/users/pat {name, scopes}` can, but the auto mode classifier refused that as a credential write, 2026-10-15).

## Diagnostics (no Docker needed)
- **Read it yourself with `npm run diagnostics`** (`scripts/diagnostics.mjs`); don't ask the user to paste it. It calls the app's `GET /diagnostics` on the active Homey through `homey api raw` (the CLI's login). Options: `-- --device <id|name>`, `--devices`, `--json`, `--debug on|off`, `--heatmap <deviceId>:<capabilityId>[:<days>]` (adds that `/history`; this starts recording a boolean, as a widget would). Right after an install the app may still be starting: retry.
- `lib/Diagnostics.ts` keeps the last 500 log lines (`app.log`/`app.error` are overridden to feed it). Errors and warnings always go to `log`; routine detail (tracking, timings, applies, load marks) goes to `debug`, logged only while the `debugLog` app setting is on (off by default; the report shows it). Services take `debug` as an optional third constructor argument (fourth in `SparklineService` and `MediaService`, which take another service second; second in `TextLineService` and `TileNameService`, which log nothing).
- The report has a section per feature (noted in each widget's note), e.g. `cameras` (every camera's images and videos: ids, types, titles; never video URLs) and `weather` (the rounded location, the last fetch, `Expires`, the last status and error).
- Load timings (`lib/Timings.ts`, debug): each request logs its total and per-step ms; a widget's first request also sends `perf=` (frame start, HTML, SDK ready, request), logged as `<Widget> widget: frame started … SDK ready 1100 ms`. Measured 2026-10-03 (phone app): Homey creates all frames at once, the HTML arrives ~0.3 s in, the SDK is ready ~1.0–1.1 s in, and each request takes ~0.4 s each way through Homey; the app answers in 0–30 ms warm, ~60–150 ms after the 10-min idle drop, ~0.2–0.4 s after an app restart. So most of a widget's load time is Homey's.
- It's also on the app settings page (`settings/index.html`; Homey app → Apps → Widgetkeeper → Configure) through `GET /diagnostics[?device=]` (pick a device for its full capability details). That page is three Homey fieldsets: API key (Save disabled while empty or checking, Enter saves, Remove only while a key is saved), Web dashboards (the on/off checkbox; while on, the address with Open and Copy, then Set/Remove password) and Diagnostics (loaded on open).

## Homey API facts (verified on the real Homey)
- Dynamic prices: `energy.fetchDynamicElectricityPrices({date: 'YYYY-MM-DD'})` → `{priceUnit: 'DKK', interval: 60, pricesPerInterval: [{periodStart, periodEnd, value}]}` (zone DK2; `getCurrency()` → `"DKK"`). Quarter-hour markets get 15-minute intervals (NL users, 2026-10-12).
  - Those are bare spot prices. Homey Energy adds the user's costs, `energy.getDynamicElectricityPriceUserCosts()` → `{mathExpression: '{{([[price]]+0.515)*1.25}}'}` (tariffs and taxes, then VAT; 2026-10-10), and no endpoint returns the prices with them. So `getPriceSettings()` reads it (with the price type, 5-min cache) and `parsePriceCosts()` (`lib/priceCosts.ts`, a small parser, no `eval`: numbers, `[[price]]`, `+ - * / % ^`, brackets, `min max abs round floor ceil`) applies it to every slot; the cached spot prices stay raw. An expression it can't read or parse leaves the spot prices, with a log line. Diagnostics' `electricity.priceCosts`. Both price widgets have `priceCosts` ("Include tariffs and taxes", on): off sends `costs=0` → `getSnapshot(…, {costs: false})`.
- Insights: `getLogEntries({uri: 'homey:device:<id>', id: 'homey:device:<id>:<cap>', resolution})`; **the `id` is the full log id.** `lastHour` has a 5 s step, `last24Hours` 5 min. `last7Days` (and `last14Days`, `thisWeek`) on a **numeric** log: `{values, start, end, step: 3600000, …}`, one average per hour, `t` the hour's start, the current hour included.
  - A **boolean** log ignores the resolution: always just the last 50 changes (`{id, values}`, `v: true/false`), whatever `resolution`, `limit` etc. say (2026-10-04). For a motion sensor that's under a day.
  - Many log reads in a row get `Too many requests.`, so every read goes through `limitInsights()` (`lib/insightsLog.ts`): at most 6 at once, app-wide.
  - **Homey logs `measure_power` as `energy_power`** on every device with it (all 462 logs checked, 2026-10-09), the only capability whose log id differs; `…:measure_power` is `Not Found: LogLocal`. `readCapabilityLog()` (Sparklines, Heatmap) tries `energy_power`, then `measure_power`, and remembers what worked. Both go through `readFirstLog()`, which the Electricity service's `readPowerLogs()` also uses (with `logIdsFor()`'s order) and `keep: true`. A busy failure (`isTransientError()`) is thrown at once, so the alias's 404 doesn't hide it and the 30-s retry works. Don't go back to `insights.getLogs()`: it lists every log on the Homey.
- The meter is a frient EMIZB-141 ("Electricity Meter", id `3450f8d3-…`): `measure_power` about every 10 s; Homey doesn't re-emit unchanged values.
- A setting removed from the manifest stays in the dashboard widget's `data.settings` (`showNextLow`, `b1Label`, `showNext`, Variables' `name1`; saving the widget's settings on the phone keeps it), but the phone app's `getSettings()` only returns the manifest's settings (2026-10-16: a fresh load of a Variables widget with `name1` stored didn't get it). So a fallback to a removed setting (the Electricity Overview's `showNextLow`) never works on the phone; only `getDashboards()` (a Smart Stack page) sees the old value.
- **A widget can't open Homey's native device sheet** (or draw over the dashboard). On the phone app (2026-10-03) the widget `Homey` has only the documented methods (`ready api on getSettings getWidgetInstanceId getDeviceIds setHeight popup hapticFeedback __`); `popup(url)` just opens an in-app browser.
  - The SDK is `/widgets/js/homey.widgets.js` on `/js/crossframe.js` (served by the Homey). Every method is `Homey._crossFrame.emit(event, data)`, posted as `CF2_MESSAGE` + UTF-16 hex JSON `{type: 'tx', event, data, callbackId}` through `window.ReactNativeWebView`; replies are `{type: 'cb', args: [err, result]}`. The events: `getInitialData` (also `fontScale`, `isDarkMode`, `transparent`, `devmode`), `ready`, `api`, `emit`, `setHeight`, `popup`, `shortPressHapticFeedback`.
  - The iOS app (2026-10-05) silently ignores unknown events: `openDevice`, `openDeviceModal`, `openDeviceSheet`, `showDevice`, `deviceOpen`, `device`, `open`, `navigate`, `openUrl`, `openURL`, `link` and `deeplink` all timed out.
  - Confirmed from the Android app's code (10.1.1, 2026-10-05): `WidgetAppWebviewFrame.handleLoad` registers exactly those events (`emit` is a no-op); `popup` and every top-frame navigation outside `/app/<appId>/widgets/` go to the in-app `BrowserView.openURL` (not `Linking`), so deep links don't work either; the only `homey://` URLs in the bundle are OAuth redirects. To re-check after an app update: the XAPK from `https://d.apkpure.com/b/XAPK/app.homey?version=latest` → `app.homey.apk` → `assets/index.android.bundle` (Hermes bytecode 98) → `hbc-disassembler` (`pip install git+https://github.com/P1sec/hermes-dec`), then search for `'getInitialData'`.
- Android text zoom (Galaxy Tab, 2026-10-04): Homey's tokens already include the system font scale (`--homey-font-size-small` = `calc(1.1 * 14px)`), and the WebView zooms all text by it again (a 100px font computes as 110px; `text-size-adjust: none` doesn't help), so token text was 1.21x against the native tiles' 1.1x. Each `index.html` runs `undoTextZoom()` first in `onHomeyReady`: it divides the `--homey-font-size-*`/`--homey-line-height-*` tokens by the measured zoom (inline on `body`). Fixed px sizes keep the zoom once, like native text. iOS has no zoom.
- Cameras (the Reolink app, 2026-10-04):
  - `device.images`: `[{type: 'camera', id: 'snapshot', title, imageObj: {id, ownerUri, url: '/api/image/<id>', lastUpdated}}]` (Sonos uses `type: 'media'` for album art); `api.images.getImages()` lists them all. `/api/image/<id>` needs no auth, from the app (`api.baseUrl` = `http://127.0.0.1:80`) or the LAN; the driver fetches the snapshot on request (~0.6 s, 0.3–2 MB JPEGs).
  - `device.videos`: `[{type: 'camera', id: 'main'|'sub', title: 'Camera (sub - h264)', videoObj: {id, type: 'rtsp'}}]`. `api.videos` is private in homey-api, but `createAppAPI` builds it. `videos.videoOffer({id, offer})` → `{answerSdp, streamId: 'video_<id>'}` from Homey's go2rtc: H.264 only, `sendonly`, host candidates on port 8555 plus public srflx ones. `videoKeepAlive({id, streamId})` keeps it going.
  - **`videos.getVideoUrl` returns the RTSP URL with the camera's password.** Never log it or put it in diagnostics.
- Widget preview images are 1024×1024; app images 250×175, 500×350 and 1000×700.

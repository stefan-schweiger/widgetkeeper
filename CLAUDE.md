# Widgetkeeper — notes for Claude

Homey Pro app (`com.thomassidor.widgetkeeper`) of custom dashboard widgets (name, id): Electricity Overview `electricity`, Thermostat Presets `thermostat`, Device Quick Actions `quickactions`, Sensor Alarms `sensoralarms`, Activity Dots `sensordots`, Room Health `roomhealth`, Weather Forecast `weather`, Insights Heatmap `heatmap`, Cameras `cameras`, Device Values `values`, Light Controls `lights`, Sparklines `sparklines`, Charts `charts`, Variables `variables`, Variable Presets `varpresets`, Flow Buttons `flows`, Energy Price Strip `price`, Timers `timers`, Locks and Doors `locks`, Curtains `curtains`, Media `media`, Clock `clock`, Notes `textline` (called Text Line while it was built), Days Since `dayssince`, Spacer `spacer` and Smart Stack `stack`. Never rename an id: it breaks widgets already on dashboards. 1.0.0 renamed Price Badge, Thermostat Shortcuts, Sensor Dots and Flow Variables to Energy Price Strip, Thermostat Presets, Activity Dots and Variables; the 0.9.0 changelog and posts keep the old names, and README.md their old anchors (`<a name>`). The electricity design spec is `temp/Homey electricity dashboard widget.zip` (`temp/` is gitignored).

## Commands
- Use the **project-local Homey CLI v4**: `npx homey …` (the global `homey` is an old 3.7.x).
- `npx homey app validate --level debug`: compiles the TS and validates.
- `npm test`: vitest in `test/` (`npm run test:watch`), run in Europe/Copenhagen. Service tests mock `homey-api` with `test/helpers/fakeHomey.ts`; widget tests run the unchanged `public/widget.js` in happy-dom (`test/helpers/loadWidget.ts`). CI (`.github/workflows/ci.yml`): typecheck, tests, validate.
- `npm run typecheck`: `tsc` for the app plus a non-strict `checkJs` pass over every `widgets/*/public/*.js` (`tsconfig.widgets.json`, which sets `strict: false` explicitly since TypeScript 7 defaults to strict; the window globals are in `types/widgets.d.ts`).
- `npm run diagnostics`: see Diagnostics.
- `npx homey app install`: builds and installs on the active Homey (firmware 13.x). `npx homey app run` (live logs, hot reload) needs Docker Desktop, which usually isn't running.
- `npm run test-dashboards [-- lights media]` (`--remove` takes them away): one web dashboard per widget type on the active Homey (`Test · <widget>`, id `test-<type>`), each widget titled by what it tests, plus a deleted device/flow/variable and an empty one where it applies. Re-running replaces those and keeps the user's own. It picks devices, flows and variables by capability and class (never by name) through the widgets' own autocompletes, and writes the app setting `webDashboards` directly (the `/web/…` API also wants the password's session). Flow Buttons only gets flows that don't look like security, alarm or lock flows: a tap starts them for real.
  - It logs in once through the CLI's own code (`homey/lib/api/ApiCommandRuntime.mjs`). Every `homey api raw` logs in through Athom's cloud, and ~30 in a row got `Too many requests` for over half an hour (2026-10-11). `HOMEY_TOKEN` (a personal API key) with `HOMEY_ADDRESS` (`http://<ip>`) skips the cloud.
- `npm run web-socket`: bundles `socket.io-client` v2 (MIT; what Homey's realtime speaks) into the committed `settings/socket.io.js` with esbuild; a test checks it's the installed version. Not `homey-api`'s browser build: its licence is proprietary.
- `npm run flow-icons`: see Flow Buttons.

## Architecture
- TypeScript, ESM (`"type": "module"`), compiled by `tsc` to `.homeybuild/`; relative imports need `.js` extensions. `app.ts` owns the services (`lib/*Service.ts`). They use `homey-api`'s `HomeyAPI.createAppAPI` (needs the `homey:manager:api` permission; the shared instance is in `lib/appApi.ts`).
- Widget front ends (`widgets/<id>/public/`) are **plain JS** with no build step: Homey serves them as-is. Every widget is three files:
  - `widget.js`: `create<X>Widget(root, opts)`, the UI. Each is an IIFE, so several share one page (the Smart Stack).
  - `mount.js`: `mount<X>Widget(Homey, {root, frame})`: the settings, `Homey.api` calls, realtime and `ready`/`setHeight` (measured on `frame`; `.frameClass` is the body's classes). The Smart Stack calls the same mounts with a slide and a Homey of its own, so keep a widget's wiring here: nothing on `document.body`, no `getElementById`. `test/widget-mount.test.ts` mounts each into a plain element with a failing Homey.
  - `index.html`: only runs `undoTextZoom()` and calls the mount with the frame's Homey and `document.body`.
- Shared back-end helpers (tested in `test/shared-service.test.ts`):
  - `lib/DeviceTracker.ts`: lazy per-device tracking for the Light, Curtain, Lock, Media, Quick Action, Sensor Alarm, Value and Thermostat services. Tracks on the first `/state`, re-reads with `$cache: false` on later ones (`readFresh()`: re-reads of one device at the same time share one `getDevice`, across every tracker and Cameras' `/state`; homey-api itself only shares `$cache: true` calls), re-tracks when `signature()` changes. A failed re-read disposes and throws, unless it failed for a passing reason (`isTransientError()`: 408, 429, 5xx, timeouts, connection errors), which keeps the entry, so a crowded dashboard's load burst doesn't show devices as missing. An entry is disposed once; a track still under way at `stop()` throws instead of subscribing; dropped after 10 min idle. `each()` is the multi-device `getState` loop with `{id, missing: true}`; also `readZones()` (one read shared for 60 s, a failure not kept) and `zoneRef()`.
  - `lib/capabilities.ts`: `describeCapability()` (an empty title falls back to the id, empty units are null), `presentCaps()`, `readCaps()`.
  - `lib/autocomplete.ts`: `matches`, `withNone`, `listDevicesWhere`, `listCapabilitySlots`, `AutocompleteItem`.
  - `lib/sharedCache.ts`: a read shared while it's at most `maxAge` old (flows, Flow cards, dashboards, Moods).
  - `lib/widgetApi.ts`: `logPerf`, `idList`, `logged`, `keyResult` for the widgets' `api.ts` handlers.
  - `lib/widgetAutocompletes.ts`: every widget's autocomplete listener in one table (`widgetAutocompletes(app)`); `app.ts` registers them with Homey and the web dashboards' editor calls the same ones. A test checks it matches the manifests.
  - `lib/widgetRoutes.ts`: `findWidgetRoute()`/`callWidgetRoute()` (a widget's own API route from the manifest, for the Smart Stack's `/call` and the web dashboards' `/web/call`) and `routeKeyUse()` (the routes that act with the stored personal API key).
  - `lib/deviceIcon.ts`: device icons (see Thermostat Presets), `homeyUrl()`, `fetchImageBase64()`, `deviceImage()` (camera snapshots, album art).
- **The usual device widget** (the widget sections only note where they differ): a `devices` setting (`singular: false`, read with `Homey.getDeviceIds()`); `GET /state?deviceIds=a,b`, one entry per id in order (`{id, missing: true}` for a deleted device), through `DeviceTracker`, so renames, changed capabilities (re-tracked) and deleted devices show on the next `/state` (an open widget used to keep its first read forever); realtime `<id>:state {deviceId, capabilityId, value}` from one capability instance per capability; tracking dropped after 10 min without `/state`, and the widget refetches every 5 min; a failed refresh keeps the tiles with a transient message (only a failed first load replaces them with the error); optimistic values for 10 s.
- **Taps** (`onTap()`, born in Quick Actions): a touch that ends within 10 px of where it started, with `click` kept for mouse and keyboard; a drag is left alone, so the dashboard still scrolls. It works on Android, where the dashboard takes drags (see the Electricity Overview).

## Widget styling
Homey's guide: https://apps.developer.homey.app/the-basics/widgets/styling. Homey injects its stylesheet into every widget frame; outside Homey (the dev previews and renders) none of its tokens is defined.
- **Frame:** `body.homey-widget` (16 px padding), `.homey-widget-small` (8) or `.homey-widget-full` (0; the transparent widgets use it). `.homey-dark-mode` is set on the frame in dark mode, about 1 s in, by the SDK.
- **Spacing:** `--homey-su` = 4 px; `--homey-su-1` … `--homey-su-8` = 4 … 32 px.
- **Type:** `--homey-font-size-small/default/large/xlarge/xxlarge` = 14/17/20/24/32 px with `--homey-line-height-*` = 20/24/28/32/40 px; `--homey-font-weight-regular/medium/bold` = 400/500/700. Natively only 14 regular, 17 any weight, 20 medium and 24/32 bold are used. The classes `.homey-text-bold/medium/regular/small/small-light` and `.homey-text-align-left/center/right` have no documented sizes, so the widgets set the variables themselves.
- **Colours:** text `--homey-text-color`, `-light` (less important or disabled), `-white`, `-blue/green/orange/red`, `-highlight/success/warning/danger`; `--homey-background-color`; the palette `--homey-color-mono-000…1000`, `--homey-color-blue/green/red-050…900`, `--homey-color-orange-500`; semantic `--homey-color-white/blue/green/orange/red/highlight/success/warning/danger`. `transparent` in `widget.compose.json` makes a see-through widget.
- **Lines, radius, icons:** `--homey-line-color(-light)` and `--homey-line(-light)` (`1px solid` that colour), `.homey-border(-top/right/bottom/left)`; `--homey-border-radius-small/default` (no documented values; our fallbacks are 3 and 14 px); icons are an SVG `mask-image` with `--homey-icon-color-dark/light/white/blue/green/orange/red` and `--homey-icon-size-small/regular/medium` = 14/16/20 px; tables `.homey-table(-striped)`.

How this project uses it:
- Every widget defines its own aliases on its root (`--ew-*`, `--tw-*`, `--qa-*` …; not `:root`, so the previews' light-mode overrides inherit), each a Homey token with the spec's dark-theme px or hex as fallback. A 4 px step uses `--homey-su-N` (a mixed padding like `8px 10px` stays px), a 20 px icon `--homey-icon-size-medium`, a 1 px line `--homey-line(-light)`. The font is set on `html`, so Homey's own on `body` wins. The settings page uses Homey's settings classes (`homey-header`, `homey-form-*`, `homey-button-*`).
- Deliberate exceptions, measured or chosen, noted per widget: the 12/16 label size (no token); the native-tile 10 px radius and dark tile fills (`#181920`, `#2B2C36`, `#2E3039`); Sensor Alarms' 14/18 text and the thermostat's 12/16 button text; the alarm and temperature colour pairs (picked to pass 4.5:1).
- Not switched, because the real values are unknown and switching could change the look: `--homey-text-color-danger` for errors (we use `--homey-color-red`), `--homey-icon-color-*` (we use the text or muted colour), `--homey-border-radius-small` for the 3 px heatmap cells, the `.homey-text-*` classes. Read the real values in a widget on the Homey before switching any.
- Copied front-end helpers are checked equal by `test/widget-html.test.ts` ('copied widget helpers'): `withName()`, `undoTextZoom()` (every index.html), `loadMarks()`/`perfParam()` (every mount.js), `onTap()` (every copy records every `touchend`, not only taps, so the click a browser still sends after a short swipe is ignored; Lights = Curtains, with a `stop` option for a control inside the tile; Flows = Activity Dots = Room Health; Timers = Locks; Media's and Variables' have no keydown on purpose; the stack's is its own), `wireBar()`, `formatSince()`, `baseTitle()`, `lowestSlot()`, `setMask()`, the dark frame block of Thermostat/Heatmap/Media/Weather and the tile/frame rim. A copy that differs on purpose is left out with a comment there.
- Checking a styling change: `npm run screenshots` before and after. Every image should be byte-identical (the clock is fixed).

## Widget settings
- Widget settings are one flat list: the phone app (Android 10.1.1's code, 2026-10-08) draws exactly `text`, `textarea`, `number`, `checkbox`, `dropdown` and `autocomplete`, each a row with its value; there's no heading or group type (an unknown type becomes a row that opens a text field). So per-tile settings are grouped by their titles: the first of each group flush left (`Button 1: flow`, `Timer 1: minutes`), the rest indented with two em spaces (U+2003) and a dash (`  – Colour`, `  – Name`). A `━━ ` rule before the first row (tried 2026-10-08) indented it past the `–` rows on iOS. Numbered titles (`Tile 4`) put a non-breaking space (U+00A0) before the number: iOS showed `Tile 4` as `Tile` (2026-10-09).
- Widgets placed before a setting existed don't have it, so the mount reads a missing value as the default: `settings.x !== false` for a checkbox that's on by default, the default for a dropdown. A setting removed from the manifest never reaches the phone's `getSettings()` again (see Homey API facts).
- An autocomplete listener gets the other settings but not the `devices` selection, so a widget whose other autocompletes depend on the device (Thermostat Presets, Insights Heatmap, Media) picks it with a `device` autocomplete and reads `settings.device.id`.

## Electricity Overview widget
- `lib/ElectricityService.ts`. The meter is the `devices` setting (`singular`, filter `capabilities: measure_power`). `GET /snapshot?deviceId=` returns the raw live readings for the last hour, 49 hourly price slots (index 24 is the current hour; the charts show the first 37, the lowest-price footer can look 24 h ahead), 5-min usage for the last ~24 h, the currency and Homey's language.
- Realtime: each meter reading as `electricity:live {deviceId, t, w}`, throttled to 1/s. Meters are tracked lazily per device and dropped after 10 min without a snapshot; widgets refetch every 5 min. A meter tracked without a readable power log looks for it again at the next usage refresh (5 min). A failed refresh keeps the last snapshot on screen.
- At app start `warmUp()` fetches the prices. Concurrent requests for a price day share one fetch; a failed day fails at once for a while (`priceFailures`: 15 min for a coming day, such as the day after tomorrow, 1 min for today). A snapshot reads the usage history alongside the prices, not after them.
- 15-minute prices (wk-034; quarter-hour markets, e.g. NL): `prices` stays hourly (the quarters' averages, `hourlyPrices()`), and `quarters` has the same span in 15-minute slots (index 96 = the current hour's first quarter; `quarterPrices()` in `lib/series.ts`, from the shortest gap between Homey's intervals, so hourly days give null), or null in hourly markets and with a fixed price. A day with only hourly prices among quarter-hour ones repeats each hour ×4; costs go on each quarter. Diagnostics' `electricity.priceInterval` is today's interval in minutes (`priceInterval()`). Our DK2 Homey gets hourly prices, so the real 15-minute path is unverified.
  - The widget keeps its hourly axis (labels, midnight lines, usage, `fineIdx`); only the price parts use the quarters (`selected()`): the step line (4 steps per hour), the band and dot on the current or scrubbed quarter (`floor(fineIdx / 3)`), the header price with `x min left` to the quarter's end and `Tue 13:15–13:30` when scrubbed, and the footer's cheapest quarter. Quarters that don't cover `prices` × 4 are ignored. `mockSnapshot({quarters: true})`.
- Front end: keep the SVG elements persistent across re-renders (replacing them breaks touch scrubbing). The drawing is the shared chart module (`chart.js` + `chart.css`, see Charts).
  - Touch: the charts `preventDefault` every `touchstart`/`touchmove` (with `touch-action: none`), else Homey's dashboard scrolls and cancels the scrub. The iOS app honours it. **Homey's Android app (a React Native WebView) doesn't:** the native dashboard takes the touch ~100 ms in, before the first `touchmove`, and sends `pointercancel` (verified with an on-screen event log on a Galaxy Tab). No widget message is sent during touches, so no widget-side fix is possible. So a tap selects (on `pointerdown`), a touch selection stays 3 s after `pointerup`/`pointercancel`, and a mouse selection resets on `pointerleave`.
  - The live chart resamples the raw readings to 120 points for the window and re-renders on a timer so it scrolls; not while `document.hidden` or off screen in a Smart Stack (`setVisible`), drawn at once when back. Charts and Sparklines do the same (Sparklines only for `document.hidden`).
- Settings: `layout` (first; `standard` or `compact`: about 350 px against 480 at 400 px wide, through `DIMS.compact` (the chip row keeps room for the top axis label) and `.ew-compact`; the price chart then thins its labels like the W scales, `LABEL_MIN_GAP`, which only happens in compact with solar export) · `liveWindow` (60/30/10/5/1/0.5 min, default 10; relative axis labels `1h · 30m · Now`) · `showPrices` (on; off leaves out the header price, the price chart and the lowest-price footer, and usage gets its own chart. Without prices set up in Homey Energy the widget looks the same with no message: the setting's hint is the only warning, since widget settings can't change with Homey's state) · `showUsage` · `separateUsage` (usage as its own chart above price, its line and dot as strong as the live trace's; on the price chart it's a thin, dimmed 1 px line) · `smooth` (off; the live and usage traces get six [1 2 1]/4 averaging passes drawn as a monotone cubic, so spikes come out lower; the price steps get 5 px rounded corners; the dots sit on the smoothed line, the header values stay real) · `nextLow` (none/12/24/both, default 12; replaced the `showNextLow` checkbox, which `index.html` still honours as a fallback, though only a Smart Stack page ever gets it: see Homey API facts) · `usageColor` (`neutral`, the text colour; or `purple`: Homey's `--theme-color-purple` from its web app stylesheet, `#7500FB` light / `#9033FC` dark, `.usage-purple` on `.ew`) · `priceCosts` (see Homey API facts).
- Where it differs from the spec:
  - Axis labels, the chart title chips and the whole footer are 12/16 (`--ew-fs-label`), matching Homey's native energy widgets (the gutters and plots were resized to match); the header subtitles (`Using now`, `min left`) stay 14, the header values 24. Dashed midnight lines on the slot charts.
  - Negative power (solar export): the W scales extend below zero in whole steps, like negative prices, with a zero line (the separate usage chart and the price chart's usage scale reach down to the 1.5th percentile, `p015()`); on the price chart the usage and price scales share the zero line. The part of a trace below zero is yellow (`--ew-export`: `#F5C518` dark, `#9A6A00` light, 4.7:1 on white), drawn twice through `exportSplit()`'s clip paths; the areas fill towards zero. The header shows `−896 W` in yellow with `Exporting now`. Without negatives the markup is unchanged. `mockSnapshot({solar: true})`.
  - The footer shows only the start hour and price (`03:00 • 1,22 kr.`). With both 12h and 24h: `Lowest 12/24h   03:00 • 1,22 / 03:00 • 1,22` (no unit), or one `03:00 • 1,22 kr.` when both are the same slot.
  - Weekday names follow Homey's language, numbers the device locale.
  - Fixed price (a user on a fixed contract): `getFixedPrice()` reads `energy.getElectricityPriceType()` (`'dynamic'`/`'fixed'`) and `getOptionElectricityPriceFixed()` (`{value: {costs: {user_fixed_base: {value: 2}}}}`, `parseFixedPrice()`), cached 5 min. `fetchDynamicElectricityPrices` still returns spot prices in fixed mode, so the type must be checked. Homey has no peak/off-peak (its app says to enter an average; 2026-10-07). The snapshot then has `fixedPrice` and every slot at that price; the widget shows the price in the header (`Fixed price` under it), hides the price chart and the footer, and draws usage as its own chart. A failed type read falls back to dynamic. Diagnostics' `electricity` section has the price type.

## Thermostat Presets widget
- Three preset buttons for one device (the `device` autocomplete); `lib/ThermostatService.ts`.
- Per button: `bNPower` (keep/on/off) and the autocompletes `bNMode`, `bNTemp` and `bNExtra`, in that order, each item `{capabilityId, value}`, read from the device's `target_temperature` range and its settable enum capabilities. Titled as in *Widget settings* (wk-066): `Button 1: power`, then `  – Mode`, `  – Temperature`, `  – Fan or other setting` (`test/locales.test.ts` checks every language).
- `GET /state?deviceId=` (re-read as the usual device widget: renames show, changed capabilities re-track, a device that can't be read is `{missing: true}`; any other failed refresh keeps the buttons with a transient error) and `POST /apply {deviceId, values}`. Realtime `thermostat:state`.
- `apply` sets `onoff=true` first and `onoff=false` last, and sends mode → temperature → extra one at a time, waiting up to 4 s for each to be reported (some drivers check the fan speed against the *current* mode). It skips values the device has right then, updating its view after each confirmed value (aircons with a setpoint per mode bring back the mode's own setpoint).
- The **Mode** field defines the mode capability (often the driver's own, not `thermostat_mode`). Without `onoff`, "turn off" becomes that mode's `off` value and "turn on" is dropped (`deviceValues()` in the widget).

## Device Values widget

- Slots `slot1`…`slot6`: autocompletes (`listSlots()`), `None` first (id `none`: an empty tile; the widget skips ids without a colon), then every device × capability as `Device · Title` (described by zone and units), id `<deviceId>:<capabilityId>` (`parseSlot()` splits on the first colon). A pair may fill several tiles; tiles are keyed by slot and position. Each `nameN` (`  – Name`) replaces the device name (`opts.names`, by position). The usual device widget's tracking, per slot.
- Shown capabilities (`valueCaps()`): `number`, `boolean`, `enum` and `string` with `getable !== false`.
- `formatValue()` (also `window.formatCapabilityValue`): numbers in the device locale to `decimals` (else at most 1), with the units (no space before `°…` and `%`); booleans `On`/`Off`; enums by their value title; `null` → `–`. A `true` boolean gets Quick Actions' blue tint.
- Percentage fill (`percentFill`, off; `redBelow` 10, `yellowBelow` 20): a `%` number (`percentOf()`) fills the tile from the left to its value (`.filled`, `--vt-fill`, a hard-stop gradient), red/yellow/green (`levelOf()`) mixed 22 % into the tile (`--vt-fill-mix`; 45 % until a user asked it to match the Flow colours). `dim` is `%` with `min: 0, max: 1` (2026-10-05), so a 0–1 `%` range is scaled to 0–100, text too (the service sends `min`/`max`).
- Icon: the capability's own `iconObj` (`fetchSvgIcon()`), else a built-in glyph by base id (thermometer, drop, bolt, sun, cloud, battery, bell for `alarm_*`, power, padlock, bulb for `dim`, wave, gauge as the fallback). `measure_battery`/`alarm_battery` always get the battery glyph (`iconFor()`, also in Sparklines; wk-029: some drivers ship a battery with a fixed fill). Homey's standard capability icons aren't public (`my.homey.app/img/capabilities/…` doesn't exist).
- Tile colour from a Flow (a user's request: a fridge blue below 5 °C and red above, internet checks green/red): the app's action card `values_set_color` ("Set the tile colour of [[slot]] to [[color]]"; `slot` autocompletes `listColorSlots()`, `listSlots()` without `None`; `color` is `default` (reset), `red`, `orange`, `yellow`, `green`, `blue` or `purple`). A Flow can't address a widget instance, so the colour belongs to the device value: every tile showing it, in any Device Values widget. `setColor()` keeps it in the app setting `valueColors` (`{'<deviceId>:<capabilityId>': colour}`) and sends `values:color {deviceId, capabilityId, color | null}`; `/state` entries carry `color` when one is set. `data-color` mixes it 22 % into the tile with the icon in the text colour, wins over `.active`, and with `percentFill` colours the fill instead of its level. Orange and blue are Homey's tokens, purple `#9033FC`, yellow `#F5C518` (no token).
- `colorStyle` (wk-051, "Colours", after `columns`): `soft` (the default; a missing or unknown value too) or `bright` (`.vt-bright`). A user found the soft yellow mustard and the orange brown (`#493F1E`, `#482E20` on the dark tile), which no hex can fix at a 22 % tint: dark yellow is olive, dark orange brown. Bright sets `--vt-fill-mix: 100%` (the same tokens and rules, at full strength) and the text and icon in `--vt-ink`: `#1A1B21` on red, orange, yellow, green and blue (5.1–10.5:1), white on purple (5.2:1); the user chose dark over white on red and blue (white on Homey's red/blue is 3.2–3.35:1). A fill ends partway, so each tile has `.vt-ink` (made only in bright, `aria-hidden`): the icon, value and name again, laid out as the tile, in the ink colour and clipped to `--vt-fill` (`clip-path: inset()`), so the text is dark over the fill and as usual beyond it (the user's choice over leaving fills soft). Not while renaming (`:not(.renaming)`), so the field stays readable. `.active` is unchanged.
- `GET /state?slots=a:cap,b:cap`: per valid slot `{deviceId, capabilityId, name, capability: {title, type, units, decimals, values, icon}, value}` or `{deviceId, capabilityId, missing: true}`. Realtime `values:state`.

The user rejected a palette, a drop, RGB circles, a rainbow-ring colour well, a dot with an icon inside, and a tinted pill while its panel is open. The user chose swatches over a wheel or hue slider, and one chip for colour and whites (it replaced a bar temperature mode). Taps only, so it works on Android. 7 columns: 7 hues at full saturation; then 5 whites with `light_temperature`, else one white (saturation 0); ✕ last. A temperature-only light gets one row of whites. The current colour has a ring (from the optimistic values). A swatch sends `{hue, saturation}` or `{temperature}` and closes it; ✕, the chip, 8 s without a touch or the light going missing close it too.
- Setting a colour: `onoff=true` first if the light was off (a Hue bridge ignores colour changes while off, so it came on in its old colour; a user's report), then `light_mode` when present (`color`/`temperature`), then `light_hue` and `light_saturation`, or `light_temperature`.
- `palette` (`PALETTES`; an unknown id → `default`): the panel's 7 colours (`[hue°, saturation]`) and 5 whites. `default` (bright colours around the wheel, whites cool → warm), `warm` (red → orange → amber → pale amber, whites warm → cool: the user's "from red to cool white"), `dusk` (indigo → violet → rose → coral → amber at 0.6–0.85 saturation, warm whites only) and `moods`.
- Room's Moods (`palette: moods`, wk-031, a user's request): the panel shows only the Homey Moods of the tile's room (`zoneOf()`: a grouped tile's zone, else its light's `zone.id`; not parent zones) and ✕, no colours or whites (the user's choice, so more Moods fit). Pills in two rows that scroll sideways (`.lc-moods`; `.one-row` while they fit in one), each with a dot of the Mood's colours (`moodDot()`). A room without Moods keeps the colours and whites; a light without colour or temperature gets the chip (the hue glyph, labelled `Moods`) while its room has Moods. No current ring. A tap closes the panel and calls `opts.onMood(id)` (`POST /mood`); the lights' realtime shows the result. `{ok: false, reason}` shakes the tile with `KEY_PROBLEMS`' message, anything else `lights.moodFailed`.
  - homey-api's `ManagerMoods`: `getMoods()` → `{[id]: {id, name, preset, zone, devices: {[deviceId]: {state}}}}` needs `homey.mood.readonly` (the app's token has it); `setMood({id})` needs `homey.mood.set`, which it lacks (2026-10-15), so starting one goes through the personal API key. Diagnostics' `moods`: counts per zone, the starts and the last error.
- `groupByZone` (off): the selected lights in one zone share a tile (`buildItems()`; id `zone:<zoneId>`, the zone's name, its first light's icon), placed where its first light is; a zone with one selected light, a light without a known zone and a missing light keep their own tile. Only the selected lights count. On while any light is; the bar shows the average brightness of those on. A tap turns all off when any is on, else all on; the bar sets every light; a colour goes to the lights with `light_hue`, a white to those with `light_temperature` and, in a room, as saturation 0 to colour lights without it. One `/set` per light, in parallel.
- Several colours (the user's request, 2026-10-15): `colorsOf()` is a tile's lit lights' colours (`colorOf()`, the shown values), without repeats, at most 4; a Homey group counts its lit lights instead of itself. With more than one, `.multi` and `setBlend()` blend them into the tile (`--lc-tint-bg`), the bar (`--lc-fill-bg`) and the chip (`--lc-pie`, `PIE_GLYPH`); `--lc-light` stays the first. ## Personal API key
- The app's token lacks `homey.logic` (Variables, Variable Presets), `homey.flow.start` and `homey.flow` (Flow Buttons, Media's buttons), `homey.mood.set` (Room's Moods) and `homey.dashboard.readonly` (Smart Stack). Diagnostics list its scopes (`apiScopes`, from `sessions.getSessionMe()`).

- The value picker (a user's request: the slots' flat `Device · Capability` list was long): the slots of Device Values, Sparklines and Charts (`picker: 'capability'`, `CAPABILITY_SLOTS` in `lib/WebDashboardService.ts`, with their autocompletes' capability filters) show the chosen value as a row (a tap changes it, ✕ empties the tile) or a Choose a value button. `chooseValue()` uses the same dialog: a device tile opens its values with their readings (`formatReading()`), and a search lists matching values at once. The data is `GET /web/values?type=` (`valueDevices()`: devices with `caps: [{id, title, type, units, decimals, min, max, values, value}]`), shared for 30 s. A choice is stored as the autocomplete's item (`{id: '<deviceId>:<capabilityId>', name: 'Device · Title', description}`), so the widgets and Homey's own settings read it unchanged.
- The page: `#/` the front page, `#/d/<id>` a dashboard (full screen and a pen in its bar), `#/d/<id>/edit` the editor.
  - Each widget is framed with its bar as the header, so it's clear which bar is whose: settings, ↑ ↓ ← →, remove with a second tap. The bar is also a drag handle (pointer events, `touch-action: none`): the widget fades in place (moving an iframe reloads it), a name pill follows the pointer, iframes get `pointer-events: none`, and a line that takes no room shows the drop point; the page scrolls near the window's edges, Escape cancels, a drop is one `moveTo()` and save. A rebuild ends a drag.
  - Add widget (per column) shows the types with their `preview-dark|light.png` (served at `/app/<appId>/widgets/<id>/`). Settings are a generic form from the manifest (the six setting types, plus the pickers). Every change is saved at once (`PUT`, queued in order, `saving`); a delete joins the queue and no save of that dashboard runs after it (`deleted`); when nothing changed meanwhile, the editor takes the app's normalized copy.
  - The grid keeps a widget's iframe while its signature (settings, devices, title, dark mode) is the same; a frame's `getInitialData` (a new document) drops the old one's realtime listeners and pending answers (`frame.gen`). One column below 720 px. **No browser dialogs** (a second tap confirms), so a wall tablet never blocks.
  - Strings: `web.*` (all 13 languages; `DEFAULT_STRINGS` must equal en's) and `settings.web*`.
- Password (optional, a user's request: an extra layer **on top of** the API key, not instead): set on the app settings page (`GET/PUT /web/password`, at least 8 characters, `''` removes it). `lib/WebPassword.ts` (`app.webPassword`): the app setting `webPassword` is `{salt, hash}` (scrypt), `webSessions` the SHA-256s of 32-byte tokens (kept over restarts, dropped after 180 days unused, at most 50). Setting, changing or removing it signs every browser out. Five wrong passwords in a row lock the login for 30 s, doubling to 15 min.
  - While set, every `/web/…` route the page uses needs `?session=<token>` (`assertWebSession()`; the query reaches GET, POST and DELETE handlers, 2026-10-11); `/web/setup` without one answers only `{passwordRequired: true, language, strings}`. `POST /web/login {password}` (`{ok, token}` or `{ok: false, reason: notSet|wrong|locked, retryAfter}`) and `POST /web/logout?session=` need the key like the rest. The page asks for the password after the key (`renderPassword()`), keeps the token in `localStorage` `widgetkeeper.web.session`, and on `password required` drops it, stops the socket and asks again (`passwordLost()`). The socket stays the key's and starts once signed in. Diagnostics' `webPassword`: set, the session count, the lock; never hashes.
- **The page must not set `color-scheme`**: an iframe whose color-scheme differs from its parent's gets an opaque white backdrop, which showed behind every transparent widget.
- `dev/web-preview.html`: the page with the simulated API (`dev/mock-web-api.js`), made-up dashboards and a house of zones and devices (library icons that exist: `light-bulb`, `plug`, `socket`, `lock`, `door` …; many names 403); `?lang=`. The frames stay empty.
- Checked on the real Homey from headless Edge (2026-10-10, 1280 × 800 and 390 px, dark and light): Lights, Timers, Electricity (live power by realtime), Energy Price Strip, Weather, Locks, the editor, the device picker and an autocomplete. Not yet on a phone, an iPad or a TV browser, with the user's own key, or away from home.

## Diagnostics (no Docker needed)
- **Read it yourself with `npm run diagnostics`** (`scripts/diagnostics.mjs`); don't ask the user to paste it. It calls the app's `GET /diagnostics` on the active Homey through `homey api raw` (the CLI's login). Options: `-- --device <id|name>`, `--devices`, `--json`, `--debug on|off`, `--heatmap <deviceId>:<capabilityId>[:<days>]` (adds that `/history`; this starts recording a boolean, as a widget would). Right after an install the app may still be starting: retry.
- `lib/Diagnostics.ts` keeps the last 500 log lines (`app.log`/`app.error` are overridden to feed it). Errors and warnings always go to `log`; routine detail (tracking, timings, applies, load marks) goes to `debug`, logged only while the `debugLog` app setting is on (off by default; the report shows it). Services take `debug` as an optional third constructor argument (`SparklineService` takes the `ValueService` second, so it's the fourth there).
- The report has a section per feature (noted in each section above), e.g. `cameras` (every camera's images and videos: ids, types, titles; never video URLs) and `weather` (the rounded location, the last fetch, `Expires`, the last status and error).
- Load timings (`lib/Timings.ts`, debug): each request logs its total and per-step ms; a widget's first request also sends `perf=` (frame start, HTML, SDK ready, request), logged as `<Widget> widget: frame started … SDK ready 1100 ms`. Measured 2026-10-03 (phone app): Homey creates all frames at once, the HTML arrives ~0.3 s in, the SDK is ready ~1.0–1.1 s in, and each request takes ~0.4 s each way through Homey; the app answers in 0–30 ms warm, ~60–150 ms after the 10-min idle drop, ~0.2–0.4 s after an app restart. So most of a widget's load time is Homey's.
- It's also on the app settings page (`settings/index.html`; Homey app → Apps → Widgetkeeper → Configure) through `GET /diagnostics[?device=]` (pick a device for its full capability details). That page is three Homey fieldsets: API key (Save disabled while empty or checking, Enter saves, Remove only while a key is saved), Web dashboards (the on/off checkbox; while on, the address with Open and Copy, then Set/Remove password) and Diagnostics (loaded on open).

## Homey API facts (verified on the real Homey)
- Dynamic prices: `energy.fetchDynamicElectricityPrices({date: 'YYYY-MM-DD'})` → `{priceUnit: 'DKK', interval: 60, pricesPerInterval: [{periodStart, periodEnd, value}]}` (zone DK2; `getCurrency()` → `"DKK"`). Quarter-hour markets get 15-minute intervals (NL users, 2026-10-12).
  - Those are bare spot prices. Homey Energy adds the user's costs, `energy.getDynamicElectricityPriceUserCosts()` → `{mathExpression: '{{([[price]]+0.515)*1.25}}'}` (tariffs and taxes, then VAT; 2026-10-10), and no endpoint returns the prices with them. So `getPriceSettings()` reads it (with the price type, 5-min cache) and `parsePriceCosts()` (`lib/priceCosts.ts`, a small parser, no `eval`: numbers, `[[price]]`, `+ - * / % ^`, brackets, `min max abs round floor ceil`) applies it to every slot; the cached spot prices stay raw. An expression it can't read or parse leaves the spot prices, with a log line. Diagnostics' `electricity.priceCosts`. Both price widgets have `priceCosts` ("Include tariffs and taxes", on): off sends `costs=0` → `getSnapshot(…, {costs: false})`.
- Insights: `getLogEntries({uri: 'homey:device:<id>', id: 'homey:device:<id>:<cap>', resolution})`; **the `id` is the full log id.** `lastHour` has a 5 s step, `last24Hours` 5 min. `last7Days` (and `last14Days`, `thisWeek`) on a **numeric** log: `{values, start, end, step: 3600000, …}`, one average per hour, `t` the hour's start, the current hour included.
  - A **boolean** log ignores the resolution: always just the last 50 changes (`{id, values}`, `v: true/false`), whatever `resolution`, `limit` etc. say (2026-10-04). For a motion sensor that's under a day.
  - Many log reads in a row get `Too many requests.`, so every read goes through `limitInsights()` (`lib/insightsLog.ts`): at most 6 at once, app-wide.
  - **Homey logs `measure_power` as `energy_power`** on every device with it (all 462 logs checked, 2026-10-09), the only capability whose log id differs; `…:measure_power` is `Not Found: LogLocal`. `readCapabilityLog()` (Sparklines, Heatmap) tries `energy_power`, then `measure_power`, and remembers what worked. Both go through `readFirstLog()`, which the Electricity service's `readPowerLogs()` also uses with its own order (`measure_power` first) and `keep: true`. Don't go back to `insights.getLogs()`: it lists every log on the Homey.
- The meter is a frient EMIZB-141 ("Electricity Meter", id `3450f8d3-…`): `measure_power` about every 10 s; Homey doesn't re-emit unchanged values.
- A setting removed from the manifest stays in the dashboard widget's `data.settings` (`showNextLow`, `b1Label`, `showNext`, Variables' `name1`; saving the widget's settings on the phone keeps it), but the phone app's `getSettings()` only returns the manifest's settings (2026-10-16: a fresh load of a Variables widget with `name1` stored didn't get it). So a fallback to a removed setting (the Electricity Overview's `showNextLow`) never works on the phone; only `getDashboards()` (a Smart Stack page) sees the old value.
- **A widget can't open Homey's native device sheet** (or draw over the dashboard). On the phone app (2026-10-03) the widget `Homey` has only the documented methods (`ready api on getSettings getWidgetInstanceId getDeviceIds setHeight popup hapticFeedback __`); `popup(url)` just opens an in-app browser.
  - The SDK is `/widgets/js/homey.widgets.js` on `/js/crossframe.js` (served by the Homey). Every method is `Homey._crossFrame.emit(event, data)`, posted as `CF2_MESSAGE` + UTF-16 hex JSON `{type: 'tx', event, data, callbackId}` through `window.ReactNativeWebView`; replies are `{type: 'cb', args: [err, result]}`. The events: `getInitialData` (also `fontScale`, `isDarkMode`, `transparent`, `devmode`), `ready`, `api`, `emit`, `setHeight`, `popup`, `shortPressHapticFeedback`.
  - The iOS app (2026-10-05) silently ignores unknown events: `openDevice`, `openDeviceModal`, `openDeviceSheet`, `showDevice`, `deviceOpen`, `device`, `open`, `navigate`, `openUrl`, `openURL`, `link` and `deeplink` all timed out.
  - Confirmed from the Android app's code (10.1.1, 2026-10-05): `WidgetAppWebviewFrame.handleLoad` registers exactly those events (`emit` is a no-op); `popup` and every top-frame navigation outside `/app/<appId>/widgets/` go to the in-app `BrowserView.openURL` (not `Linking`), so deep links don't work either; the only `homey://` URLs in the bundle are OAuth redirects. To re-check after an app update: the XAPK from `https://d.apkpure.com/b/XAPK/app.homey?version=latest` → `app.homey.apk` → `assets/index.android.bundle` (Hermes bytecode 98) → `hbc-disassembler` (`pip install git+https://github.com/P1sec/hermes-dec`), then search for `'getInitialData'`.
- Android text zoom (Galaxy Tab, 2026-10-04): Homey's tokens already include the system font scale (`--homey-font-size-small` = `calc(1.1 * 14px)`), and the WebView zooms all text by it again (a 100px font computes as 110px; `text-size-adjust: none` doesn't help), so token text was 1.21x against the native tiles' 1.1x. Each `index.html` runs `undoTextZoom()` first in `onHomeyReady`: it divides the `--homey-font-size-*`/`--homey-line-height-*` tokens by the measured zoom (inline on `body`). Fixed px sizes keep the zoom once, like native text. iOS has no zoom.
- Cameras (the Reolink app, 2026-10-04):
  - `device.images`: `[{type: 'camera', id: 'snapshot', title, imageObj: {id, ownerUri, url: '/api/image/<id>', lastUpdated}}]` (Sonos uses `type: 'media'` for album art); `api.images.getImages()` lists them all. `/api/image/<id>` needs no auth, from the app (`api.baseUrl` = `http://127.0.0.1:80`) or the LAN; the driver fetches the snapshot on request (~0.6 s, 0.3–2 MB JPEGs).
  - `device.videos`: `[{type: 'camera', id: 'main'|'sub', title: 'Camera (sub - h264)', videoObj: {id, type: 'rtsp'}}]`. `api.videos` is private in homey-api, but `createAppAPI` builds it. `videos.videoOffer({id, offer})` → `{answerSdp, streamId: 'video_<id>'}` from Homey's go2rtc: H.264 only, `sendonly`, host candidates on port 8555 plus public srflx ones. `videoKeepAlive({id, streamId})` keeps it going.
  - **`videos.getVideoUrl` returns the RTSP URL with the camera's password.** Never log it or put it in diagnostics.
- Widget preview images are 1024×1024; app images 250×175, 500×350 and 1000×700.

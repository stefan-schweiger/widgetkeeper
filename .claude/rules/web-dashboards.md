# Web dashboards

- Our widgets (and other apps', below) in any browser on the home network, on dashboards laid out on the page itself (the user's choice over reusing Homey dashboards; home network only; a personal API key per browser). `settings/dashboard.html` (+ `dashboard.js`, `dashboard.css`, `socket.io.js`), served by the Homey without login at `http://<ip>/app/<appId>/settings/dashboard.html`. The app settings page shows the address (`GET /web/address`, `homey.cloud.getLocalAddress()`). It loads the kit as `../widgets/spacer/kit.js` (and `.css`), the Homey's path, not the repo's `public/` one (a 404 on the Homey, which left `WidgetkeeperKit` undefined and the value slots empty, 2026-10-18); the dev pages load their own. `lib/WebDashboardService.ts` keeps the dashboards.
- Each widget runs **unchanged** in an iframe of its own `../widgets/<id>/index.html?widgetInstanceId=web-<dashboardId>-<widgetId>`: the Homey injects its SDK (`/js/crossframe.js`, `/widgets/js/homey.widgets.js`) and stylesheet (`/widgets/css/homey.widgets.css`, which the page loads too: Homey's real tokens, fonts and `.homey-dark-mode`) into every served widget `index.html`. Outside a WebView the SDK's crossframe posts to `window.parent`, so the page answers it as Homey's dashboard does: `getInitialData` (`{settings, deviceIds, transparent, locales, language, devmode, fontScale, isDarkMode}`), `api` (→ `POST /web/call {type, method, path, query, body}` → the widget's own `api.ts`, `callWidgetRoute()`), `registerRealtimeListener` (data is the event name; every event is a `cb` with `args: [data]` and that callbackId), `ready`/`setHeight` (the iframe's height), `popup`, `shortPressHapticFeedback`, `emit`. Messages are `CF2_MESSAGE` + UTF-16 hex JSON (`hexEncode()` through a byte table); an error is `{type: 'Error', data: message}`. The iframes are `loading="lazy"`.
- Requests: `fetch('/api/app/<appId>/…', {Authorization: 'Bearer <key>'})`, same origin (a personal API key may call the app's API, 2026-10-10). The key is `localStorage` `widgetkeeper.web.key`; a 401/403 forgets it, stops the socket and brings the key screen back. The app's own token still does everything else. A route that acts with the stored key (`routeKeyUse()`: variables `/set`, flows `/trigger`, media `/button` (a `card:` needs `homey.flow`), stack `/pages`, lights `/mood`, and a stack `/call` of those) only runs when the page's own key may do the same: `/web/call` carries `key`, and `PersonalApiKey.scopesOf()` reads its scopes (remembered 60 s; a passing failure throws and isn't kept). `/web/autocomplete` carries it too, for the Smart Stack's dashboards (`autocompleteKeyUse()`); else `{ok: false, reason: keyScope | keyInvalid}`, so a weaker key can't borrow the stored one's permissions.
- Realtime without homey-api: socket.io v2 to the Homey (`transports: ['websocket']`), `emit('handshakeClient', {token, homeyId}, cb)` → `{namespace: '/api'}`, `io.socket(namespace)` and `.open()`, `emit('subscribe', 'homey:app:<appId>', cb)`, then events arrive as `ns.on('homey:app:<appId>', (event, data))` (2026-10-10). `homeyId` comes from `/web/setup` (`homey.cloud.getHomeyId()`). Any failure or disconnect starts over (2 s, doubling to 60 s); after an outage over 30 s the frames reload. `No live updates` shows while it's down.
- Endpoints (`api.ts`): `GET /web/setup` (`{appId, homeyId, language, strings, widgets: widgetTypes(), dashboards}`), `GET /web/devices?type=&query=` (the manifest's `devices.filter`: `class`/`capabilities` as `a|b`, the class or the virtual class; `{id, name, zone: {id, name, path} | null, icon}`, the icon the same-origin `/api/icon/<id>` (no login needed) or the library URL), `GET /web/values?type=`, `POST /web/autocomplete {type, setting, query, settings}`, `PUT /web/dashboards` (a new one gets an id), `DELETE /web/dashboards/:id`, `POST /web/call`, `GET /web/address`, and the password routes.
- On/off: the app setting `webDashboardsEnabled` (off unless `true`), a checkbox on the settings page, which shows the address only while it's on. Off, `/web/setup` answers only `{disabled: true, language, strings}` (`web.off`) and every other `/web/…` route but `/web/address` throws `Web dashboards are turned off` (`assertEnabled()`); the dashboards stay. The page's `failed()` goes back to `start()` on that error.
- Storage: the app setting `webDashboards`, `[{id, name, theme: auto|dark|light, columns: [[{id, type, title, settings, deviceIds, trusted?}]]}]`. `normalize()` keeps known types and only the manifest's setting ids (the default where missing or wrong; an autocomplete choice keeps its own fields, e.g. the thermostat's `capabilityId`/`value`, without `image`), one device for a singular devices setting; 1–6 columns, 60 widgets, 30 dashboards.
- The front page (`#/`, a user's request for something prettier): `Widgetkeeper Web Dashboards` (`brand()`) after the app icon (`LOGO`, white on `#2A1958`; also the inline SVG favicon, a user's request), the dashboards as cards (`dashboardCard()`: a miniature of the columns from the widgets' previews; the card opens it, a pen edits it), a New dashboard card, then the widget types one at a time in a small, quiet carousel (`widgetCarousel()`: the preview, the name, `web.about.<type>` (all 13 languages, tested; also in Add widget), ‹ ›). A user found an earlier row of large previews took the attention from the dashboards, then a 90 px one too small. It cross-fades every 6 s, but not while hovered or focused, for 15 s after a tap, while hidden, or with reduced motion.
- The device picker (a user's request: more room, grouped by room): the settings list the chosen devices in order (drag the grip to reorder, ✕ drops one) with a Choose/Change button that opens `chooseDevices()`: a large dialog with a search, room chips (All rooms, Chosen, each room) and each room's devices as tiles. One device: a tap picks it and closes; several: taps tick (Select all/Clear all per room; Done or Cancel). A widget just added with a devices setting opens it at once (`editWidget(id, {pickDevices: true})`).
- The value picker (a user's request: the slots' flat `Device · Capability` list was long): the slots of Device Values, Sparklines and Charts (`picker: 'capability'`, `CAPABILITY_SLOTS` in `lib/WebDashboardService.ts`, with their autocompletes' capability filters) show the chosen value as a row (a tap changes it, ✕ empties the tile) or a Choose a value button. `chooseValue()` uses the same dialog: a device tile opens its values with their readings (`formatReading()`), and a search lists matching values at once. The data is `GET /web/values?type=` (`valueDevices()`: devices with `caps: [{id, title, type, units, decimals, min, max, values, value}]`), shared for 30 s. A choice is stored as the autocomplete's item (`{id: '<deviceId>:<capabilityId>', name: 'Device · Title', description}`), so the widgets and Homey's own settings read it unchanged.
- The page: `#/` the front page, `#/d/<id>` a dashboard (full screen and a pen in its bar), `#/d/<id>/edit` the editor.
  - Each widget is framed with its bar as the header, so it's clear which bar is whose: settings, ↑ ↓ ← →, remove with a second tap. The bar is also a drag handle (pointer events, `touch-action: none`): the widget fades in place (moving an iframe reloads it), a name pill follows the pointer, iframes get `pointer-events: none`, and a line that takes no room shows the drop point; the page scrolls near the window's edges, Escape cancels, a drop is one `moveTo()` and save. A rebuild ends a drag.
  - Add widget (per column) shows the types with their `preview-dark|light.png` (served at `/app/<appId>/widgets/<id>/`).
  - The settings dialog (`editWidget()`; a user found the old flat form of 33 equal rows impossible to get an overview of, 2026-10-18): a header with the widget's preview and `web.about.<type>`, then cards on the dashboard's backdrop: Devices (the chosen list, Choose/Change in the card's header), the title with the first plain settings, then the manifest's sections in order. `settingSections()` (`lib/WebDashboardService.ts`; a copy in `dev/mock-web-api.js`, keep them alike) reads them from the English titles' convention (CLAUDE.md, *Widget settings*) and gives each setting its `label`: `plain` runs; a `group` (a head and its `  – ` rows; numbered ones like `Button 1` share one card and fold, more than two in a run start folded, the header shows a summary: the choices' names, dropdown titles with a colour dot, texts, a number head as `5 minutes`; an empty autocomplete head dims the title); a not-numbered group under a checkbox (the stack's page dots) fades and goes `inert` while it's off; `slots` (`Tile 1…6`, the first's hint above them). Rows: label and hint on the left, a short control on the right (a switch for a checkbox, swatches for a dropdown of the widgets' colour names, segments for ≤ 3 short values, a compact select, a number with the unit from its title's `(…)`, a text field), or a wide control under them (textarea, the pickers). One column of everything below 560 px. Draft, Save and Cancel as before; a setting missing from the widget starts at the manifest's default. Every change is saved at once (`PUT`, queued in order, `saving`); a delete joins the queue and no save of that dashboard runs after it (`deleted`); when nothing changed meanwhile, the editor takes the app's normalized copy.
  - The grid keeps a widget's iframe while its signature (settings, devices, title, dark mode) is the same; a frame's `getInitialData` (a new document) drops the old one's realtime listeners and pending answers (`frame.gen`). One column below 720 px. **No browser dialogs** (a second tap confirms), so a wall tablet never blocks.
  - Strings: `web.*` (all 13 languages; `DEFAULT_STRINGS` must equal en's) and `settings.web*`.
- Password (optional, a user's request: an extra layer **on top of** the API key, not instead): set on the app settings page (`GET/PUT /web/password`, at least 8 characters, `''` removes it). `lib/WebPassword.ts` (`app.webPassword`): the app setting `webPassword` is `{salt, hash}` (scrypt), `webSessions` the SHA-256s of 32-byte tokens (kept over restarts, dropped after 180 days unused, at most 50). Setting, changing or removing it signs every browser out. Five wrong passwords in a row lock the login for 30 s, doubling to 15 min; sign-ins are checked one at a time, so a burst of guesses can't all pass the lock.
  - While set, every `/web/…` route the page uses needs `?session=<token>` (`assertWebSession()`; the query reaches GET, POST and DELETE handlers, 2026-10-11); `/web/setup` without one answers only `{passwordRequired: true, language, strings}`. `POST /web/login {password}` (`{ok, token}` or `{ok: false, reason: notSet|wrong|locked, retryAfter}`) and `POST /web/logout?session=` need the key like the rest. The page asks for the password after the key (`renderPassword()`), keeps the token in `localStorage` `widgetkeeper.web.session`, and on `password required` drops it, stops the socket and asks again (`passwordLost()`). The socket stays the key's and starts once signed in. Diagnostics' `webPassword`: set, the session count, the lock; never hashes.
- **Other apps' widgets** (a user's request, 2026-10-18; on the branch `web-other-apps` until the user decides to publish): a widget's `type` is then Homey's id `homey:app:<appId>:<widgetId>` (`foreignWidget()` server-side, `appWidget()` on the page; our own app's id in that form is dropped). The page does everything for them **directly with its own key** (`homeyRequest()`, `/api/…` without `session`; a 403 there is `scope`, not a rejected key), all checked on the Homey 2026-10-18:
  - The list: `GET /api/manager/dashboards/appwidget` (`getAppWidgets()`, `homey.dashboard.readonly`, so a full-access key only): `{<id>: {id, ownerUri, ownerName, name, devices: {type: 'app'|'global', singular, filter} | null, settings: [{id, type, title, hint, placeholder, values, units, value}], height, transparent, deprecated}}`, titles already in Homey's language; no API routes or icons. 16 of 43 were other apps' on the test Homey. `loadAll()` asks for it beside `/web/setup`; without it (`foreignState` `noScope`/`failed`) Add widget says so and existing ones still draw (as a card, the default height) but can't be edited. One no longer listed shows `web.notInstalled`. Deprecated ones aren't offered.
  - Files: `/app/<appId>/widgets/<id>/index.html` and `preview-dark|light.png`, no login, with the SDK injected (Mi Flora's). The Homey sends `Access-Control-Allow-Origin: *` on them and on `/widgets/js/homey.widgets.js` (a module script, so a sandboxed frame needs it).
  - Their API: `/api/app/<appId>/widget/<widgetId>/api<path>` (not `/widgets/`; found by trying with our Clock's `/clock`). `appApi()` refuses a path that resolves outside it (`..`), or a sandboxed widget could use the key for any route.
  - Autocompletes: `GET /api/manager/dashboards/appwidget/<id>/autocomplete?settingId=&query=&settings[…]` (`bracketQuery()`). Strings for `Homey.__`: `GET /api/manager/apps/app/<appId>/locale` (`homey.app.readonly`; `{}` on failure), per app. Realtime: `subscribe` to `homey:app:<appId>` on the same namespace once one of its frames listens (`listenToApp()`, again on every new socket); listeners are keyed `<uri>\n<event>`.
  - The server stores them without a manifest (`foreignSettings()`: ≤ 60 plain values or autocomplete items, no reserved keys) and lists their devices by the filter the page sends (`/web/devices?type=&class=&capabilities=&app=1`, `app` meaning `deviceApp()` is that app).
  - **Sandboxed** (`SANDBOX`: scripts, forms, popups; no `allow-same-origin`, the user's choice): an opaque origin, so they can't read `localStorage`'s key or the page; the page posts to them with `'*'`. A sandboxed widget can't use its own `localStorage` or cookies, so the settings have **Trust this widget** (`trusted: true` on the widget, the only extra field the server keeps), which runs it same-origin. Checked in headless Edge with Mi Flora's real widget in a sandboxed frame of `dev/web-preview.html`: origin `null`, `getInitialData`, `ready {height: 188}`, then its `/devices` call.
  - Their settings are one plain card (their titles don't follow our convention); a number's `units` go in the label's `(…)`. `dev/mock-web-api.js` has a made-up app (`com.example.garden`, "Garden Helper") with two widgets.
  - Not yet tried: on the real page with a personal key (whether a key's other app routes and `subscribe` need more than ours), a widget with devices or an autocomplete, realtime from another app, and how many other apps' widgets break sandboxed.
- **The page must not set `color-scheme`**: an iframe whose color-scheme differs from its parent's gets an opaque white backdrop, which showed behind every transparent widget.
- `dev/web-preview.html`: the page with the simulated API (`dev/mock-web-api.js`), made-up dashboards and a house of zones and devices (library icons that exist: `light-bulb`, `plug`, `socket`, `lock`, `door` …; many names 403); `?lang=`. The frames stay empty.

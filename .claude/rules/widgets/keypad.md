# Keypad widget (`keypad`)

- Up to three buttons behind an optional 3–6 digit code, each starting a Flow or setting the state the widget shows (the user's request, 2026-10-25: alarm arming, unlocking doors, allowing TV time). The look is **K · Split** of the user's directions (`temp/keypad-directions-3.html`; A–J in `-.html`/`-2.html`, none of which they took): the state on the left (the lit button's icon in its colour, 36 px; the state 24 bold, two lines; the title or the source's name, 14 muted), a line, and the buttons stacked on the right (40 px, the key fill, icon, label, a tick on the lit one, the keypad dots `⠿` on one that wants the code). Unlike the Presets row on purpose (the user didn't want a third widget that looks alike). Not transparent: `homey-widget kp-frame`, the thermostat's dark frame copied (`test/widget-html.test.ts` checks). `lib/KeypadService.ts` (`app.keypad`, deps flows, values, variables). Plan: `temp/keypad-plan.md`.
- **Settings (23):** `title`, `state` ("State from": `listSources()`: `None`, the Logic variables as `var:<id>` (described `Variable · …`), then Device Values' `listSlots()` as `cap:<deviceId>:<capabilityId>`; `parseSource()`), `code` (below), `layout` (the thermostat's), `colorStyle`, then per button N = 1–3 `flowN` (`Button 1: flow`, Flow Buttons' `listFlows()`), `valueN` (`  – Value`), `labelN`, `iconN` (Flow Buttons' icons, `none` allowed), `colorN` (Flow Buttons' seven, grey keeps the key) and `codeN` (`  – Needs the code`, on by default). The manifest was generated from Variable Presets' and Flow Buttons' translations (a one-off script; edit the JSON now).
- **`valueN`** (`listStateValues(settings.state.id, query)`; throws `keypad.selectStateFirst` without a state): a variable's are Variable Presets' `listPresetValues()`; a list capability's values by title; yes/no in the capability's words (`BOOLEAN_WORDS`: `locked` Locked/Unlocked, `garagedoor_closed`/`windowcoverings_closed` Closed/Open, `alarm_contact` Open/Closed, else On/Off; the widget has the same table, `window.keypadBooleanWords`, checked equal); a number or text as typed, then the current value. Items keep `value` and `type` (`typeof`), id `<type>:<json>`, described `Current value` and, for a capability that's `setable: false`, `keypad.cantSet`.
- **A button** (`keypadSettings()`): one with a Flow or a value. A tap with a Flow starts it (the personal key's Start Flows); without one it sets the state to its value: a variable through Variables' service (the key's Variables), a capability with the app's own token, checked like Locks' `set()` (it exists, `setable !== false` else `notSetable`, `checkCapabilityValue()`: an enum's own id, a number within min/max, a boolean, a text ≤ 200). The lit button is the one whose value the state has (`sameValue`, Variable Presets'); the Flow is expected to change the state itself. A set value shows for 10 s or until it's reported (`optimistic`). Label: `labelN`, else the Flow's name (`/state`'s, else the setting item's), else the value's name. A missing, off or not-triggerable Flow is dimmed; a tap only says so (Flow Buttons' strings).
- **Automatic buttons** (the user's choice, 2026-10-25): no button set up and a list or yes/no state gives one per value (at most 4), named by its title, all wanting the code when one is set; `KNOWN` icons and colours for `homealarm_state` (armed shield red, partially_armed home orange, disarmed unlock green) and `locked` (lock green, unlock red), else grey without an icon. Nothing at all: `selectButtons`.
- **The code:** the `code` setting is an autocomplete (`codeItems()`): typing 3–6 digits offers one item named by dots (`••••`), described `A 4-digit code`, `digits: 4`, id `code:v1:<key tag>:<salt>:<hmac>` (HMAC-SHA256 of `<salt>:<code>`, 128 bits, keyed with `keypadKey`, 32 random bytes in `/userdata/secrets.json`, made with the first code; the tag is 8 hex of the key's SHA-256). The digits are never stored, logged or sent back. `checkCode()` (`timingSafeEqual`): wrong ones count per code id (the oldest of 200 dropped), the fifth in a row locks it 30 s, doubling to 15 min (the web password's rule, in memory); a code of another key (the app reinstalled, the secret lost) or not one is `codeReset`. The README says plainly it guards the dashboard, not the Homey (anyone who can open the Homey app can start the Flow there; the route trusts the widget as Locks' `/set` does).
- **The pad** (`openPad()`): comfortable in the right half (the state stays in view: the left's subtitle carries its messages), 3×4 keys of 34 px (1–9, a blank, 0, ⌫); compact in place of the whole widget, the label, the title or a message, the dots and ✕ on top, then two rows of six (1–5 ⌫ / 6–0). It knows the length (`digits`) and sends on the last digit (dots pulse, keys off). Answers: `done` closes it and ticks the button; `wrongCode` red dots for 0.7 s, `Wrong code`, or `Wrong code. Tries left: n` from 2 left; `locked` turns the keys off with a countdown (`lockedOut`, kept for the widget, so reopening shows it); `codeReset` says to set it again and takes no more digits; a key problem or a failure closes it, shakes the button and says why. Number keys, Backspace and Escape on the document while it's open (web dashboards); ✕, Escape or 30 s alone close it (not while checking). The widget grows with it (`onHeight`).
- `GET /state?source=&flows=a,b` → `{source, flows}`: a variable `{kind: 'variable', id, name, type, value}`, a capability `{kind: 'capability', deviceId, capabilityId, name, capability, value}` (Device Values' entry), either `{…, missing: true}`; flows Flow Buttons' entries, `null` when they couldn't be read (the widget keeps the last). `POST /press {flow} | {source, value}` with `{codeId, code}` when the button wants it → `{ok: true, result: done | wrongCode (left) | locked (retryAfter) | codeReset | notSetable}` or, through `keyResult()`, `{ok: false, reason}`. `routeKeyUse()`: `flows` with a Flow (and for a body with neither, as the web test asks), `variables` for a `var:` source, null for a `cap:` one, which `DEVICE_WRITES` covers (the browser key's device control). Realtime: the mount follows `values:state` for its capability and `variables:state` for its variable; refetches every 5 min and when the page becomes visible.
- Not a Smart Stack page (the pad grows the widget, not tried in a slide; `test/stack-service.test.ts`). No Flow cards yet (a *Wrong code* trigger was suggested). Diagnostics' `keypad`: whether the key exists, presses, wrong codes, lockouts, codes locked now, the last error; never codes or hashes.
- Strings `keypad.*` (the service's too: `variable`, `selectStateFirst`, `cantSet`, `codeHint`, `codeDigits`); the kit got an `unlock` icon (`flows.icons.unlock` "Open lock", `lib/flowIconImages.ts` re-rendered for it only).
- `dev/keypad-preview.html` (made-up alarm, door and TV time; code 1234, five wrong lock it 30 s; `?open=0,10` opens those cases' pads with two digits typed). The README screenshot is inline in `mock-dashboard.js` (a made-up alarm, armed). `npm run test-dashboards -- keypad`: a speaker's `speaker_repeat` (a list like an alarm's state, harmless; never an alarm or a lock, a tap sets it), a yes/no variable, harmless flows (`RISKY_FLOW`), codes 1234 and 123456 typed into the code autocomplete.
- Colour style (`colorStyle`, Muted/Vivid; CLAUDE.md *Widget styling*, `kit.css`): the buttons' `data-wk-color`. The lit button: Muted its colour mixed 22 % into the card (a tinted widget, as the mockup), Vivid the shade, solid, with `--wk-on-shade` text; grey a lighter key. The left icon is `--wk-c-bright` in both.

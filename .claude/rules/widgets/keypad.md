# Keypad widget (`keypad`)

- Up to three buttons behind an optional 3–6 digit code, each starting a Flow or setting the state the widget shows (the user's request, 2026-10-25: alarm arming, unlocking doors, allowing TV time). The look is **K · Split** of the user's directions (`temp/keypad-directions-3.html`; A–J in `-.html`/`-2.html`, none of which they took): the state on the left (the lit button's icon in its colour, 36 px; the state 24 bold, two lines; the title or the source's name, 14 muted), a line, and the buttons stacked on the right (40 px, the key fill, icon, label, a tick on the lit one, the keypad dots `⠿` on one that wants the code). Unlike the Presets row on purpose (the user didn't want a third widget that looks alike). Not transparent: `homey-widget kp-frame`, the thermostat's dark frame copied (`test/widget-html.test.ts` checks). `lib/KeypadService.ts` (`app.keypad`, deps flows, values, variables). Plan: `temp/keypad-plan.md`.
- **Settings (24):** `title`, `state` ("State from": `listSources()`: `None`, the Logic variables as `var:<id>` (described `Variable · …`), then Device Values' `listSlots()` as `cap:<deviceId>:<capabilityId>`; `parseSource()`), `code` (`codeItems()`: `None`, Any code (`any`, `ANY_CODE`, described `Any of the N codes`), then the codes made on the app settings page by name, described `A 4-digit code`; none yet: `None` saying where to add one), `keypad` ("Show the keypad": `tap` "When a button needs it", `always`), `layout` (the thermostat's), `colorStyle`, then per button N = 1–3 `flowN` (`Button 1: flow`, Flow Buttons' `listFlows()`), `valueN` (`  – Value`), `labelN`, `iconN` (Flow Buttons' icons, `none` allowed), `colorN` (Flow Buttons' seven, grey keeps the key) and `codeN` (`  – Needs the code`, on by default; only with a code picked). The manifest was generated from Variable Presets' and Flow Buttons' translations (one-off scripts; edit the JSON now).
- **`valueN`** (`listStateValues(settings.state.id, query)`; throws `keypad.selectStateFirst` without a state): a variable's are Variable Presets' `listPresetValues()`; a list capability's values by title; yes/no in the capability's words (`BOOLEAN_WORDS`: `locked` Locked/Unlocked, `garagedoor_closed`/`windowcoverings_closed` Closed/Open, `alarm_contact` Open/Closed, else On/Off; the widget has the same table, `window.keypadBooleanWords`, checked equal); a number or text as typed, then the current value. Items keep `value` and `type` (`typeof`), id `<type>:<json>`, described `Current value` and, for a capability that's `setable: false`, `keypad.cantSet`.
- **A button** (`keypadSettings()`: `{sourceId, codeId, keypad, buttons}`): one with a Flow, a value, or only a label (the user's, 2026-10-25, with the trigger: it only fires the trigger; `{}` to `/press` is `done`; never lit, no optimistic value). A tap with a Flow starts it (the personal key's Start Flows); without one it sets the state to its value: a variable through Variables' service (the key's Variables), a capability with the app's own token, checked like Locks' `set()` (it exists, `setable !== false` else `notSetable`, `checkCapabilityValue()`: an enum's own id, a number within min/max, a boolean, a text ≤ 200). The lit button is the one whose value the state has (`sameValue`, Variable Presets'); the Flow is expected to change the state itself. A set value shows for 10 s or until it's reported (`optimistic`). Label: `labelN`, else the Flow's name (`/state`'s, else the setting item's), else the value's name. A missing, off or not-triggerable Flow is dimmed; a tap only says so (Flow Buttons' strings).
- **Automatic buttons** (the user's choice, 2026-10-25): no button set up and a list or yes/no state gives one per value (at most 4), named by its title, all wanting the code when one is picked; `KNOWN` icons and colours for `homealarm_state` (armed shield red, partially_armed home orange, disarmed unlock green) and `locked` (lock green, unlock red), else grey without an icon. Nothing at all: `selectButtons`.
- **The codes** (the user found typing the code into the widget's settings terrible and chose the app settings page, 2026-10-25; it was an autocomplete keeping an HMAC per widget before): **Apps → Widgetkeeper → Configure → Keypad codes** (`settings/index.html`, after the API key): its card's line lists the codes' names; inside, a row per code (the name, `N digits`, Change, Remove with a second tap within 4 s), then Add code, which opens a form: Name, Code and The code again (`type="password"`, `inputmode="numeric"`, digits only as typed, at most 6), Add code and Cancel; Change opens it with Current code in place of the name and Save code. App routes: `GET /keypad-codes` (`{codes: [{id, name, digits}]}`), `POST /keypad-codes {name, code}`, `PUT /keypad-codes/:id {current, code}`, `DELETE /keypad-codes/:id` (each `{ok, codes}` or `{ok: false, reason: name | nameTaken | digits | full | missing | wrongCode | locked (retryAfter)}`). The secret `keypadCodes` in `/userdata/secrets.json`: `[{id (12 hex), name (≤ 40, unique ignoring case), digits, salt, mac}]`, at most 20 (`MAX_CODES`); `mac` is HMAC-SHA256 of `<salt>:<code>` (128 bits) keyed with `keypadKey` (32 random bytes, made with the first code). The digits are never stored, logged or sent back. **Changing takes the current code** (the settings page can't tell the owner from anyone whose key may call the app, and a changed code would let them in at the widget), and it counts toward that code's lock; **removing doesn't** (it only locks its buttons: a widget whose code is gone refuses them with `codeMissing` until another is picked in its settings, so a forgotten code can go). `checkCode()`/`check()` (`timingSafeEqual`): wrong ones count per code, the fifth in a row locks it 30 s, doubling to 15 min (the web password's rule, in memory). A lost key makes every code wrong (remove and add them again). The README says plainly it guards the dashboard, not the Homey (anyone who can open the Homey app can start the Flow there; the route trusts the widget as Locks' `/set` does).
  - **Any code** (the user's request, 2026-10-25: a code's name identifies a person, as a tag in Flows; their choice of Any code only over groups): every code works; `check()` compares every code of the typed length (`find()`), says which (`entry`), and counts wrong ones under `any`. `codeInfo('any')`: `{id: 'any', name: 'Any code', digits}`, `digits` null while the codes' lengths differ (the keypad's bottom-left key is then OK, and Enter; the dots are only those typed, at most 6; Always: a button tapped after 3+ digits sends them, OK alone says `Now tap a button`); `{missing: true}` while there's no code (`noCodes`). **No two codes share digits** (`codeTaken`, `kpCodeTaken`), so the name is whose; since that tells whether digits are taken, every add and change counts (`EDITS`: ten, then locked like wrong codes, forgotten after an hour without one), so the route can't be used to guess codes.
- **The keypad** (the user's ask, 2026-10-25: always a proper keypad): a phone's 3×4 in every layout, 1–9, then the bottom row: nothing (on a tap) or ✕ to clear (always shown), 0 and ⌫. Above the keys: the button's icon and label (or the prompt), the dots (the code's length from `/state`'s `code`) and, on a tap, ✕ to close. It sends on the last digit (dots pulse, keys off). The dot the next digit fills (`.next`) has the button's colour and pulses while the keypad waits (still with reduced motion); while Any code's length isn't known, the digits typed and one more show.
  - **On a tap** (`keypad: tap`): a button behind the code opens it, comfortable in the right half (the state stays in view: the left's subtitle carries its messages, 34 px keys), compact in place of the whole widget (the label, the title or a message, the dots, ✕; 44 px keys, the grid at most 264 px wide). ✕, Escape or 30 s alone close it (not while checking); the keyboard is the document's only while open.
  - **Always** (`keypad: always`, with a code picked; the user's ask): comfortable has the state with the buttons under it on the left and the keypad on the right (the prompt on its own line, the dots centred); compact the state and square buttons on top, the keypad under them. The prompt and the dots are centred over the keys, a phone's lock screen (the user found the open keypad didn't say plainly enough that it wanted the code, 2026-10-25); the prompt says what for (`prompt()`): `Enter the code for <label>` with its icon for the button waiting or the only one behind the code, else `Enter the code, then tap a button`. Type the code, then tap the button, or tap the button first (it's ringed, `.target`; a second tap lets go); with one button behind the code, a complete code alone runs it, else the prompt says `Now tap a button`. A button without the code runs at once whatever was typed. ✕, Escape or 30 s alone clear the digits and the waiting button. The keyboard is always the document's.
  - Answers: `done` closes it (on a tap) or clears it and ticks the button; `wrongCode` red dots for 0.7 s, `Wrong code`, or `Wrong code. Tries left: n` from 2 left (the waiting button stays); `locked` turns the keys off with a countdown (`lockedOut`, kept for the widget); `codeMissing` says so and takes no more digits; a key problem or a failure closes it, shakes the button and says why. The widget grows with it (`onHeight`).
- `GET /state?source=&flows=a,b&code=` → `{source, flows, code}`: a variable `{kind: 'variable', id, name, type, value}`, a capability `{kind: 'capability', deviceId, capabilityId, name, capability, value}` (Device Values' entry), either `{…, missing: true}`; flows Flow Buttons' entries, `null` when they couldn't be read (the widget keeps the last); `code` `{id, name, digits}`, `{id, missing: true}` or null. `POST /press {flow} | {source, value} | {}` with `{codeId, code}` when the button wants it, and `{button, title}` (its label, the widget's title or the state's name) for the trigger → `{ok: true, result: done | wrongCode (left) | locked (retryAfter) | codeMissing | notSetable}` or, through `keyResult()`, `{ok: false, reason}`. `routeKeyUse()`: `flows` with a Flow (and for a body with neither, as the web test asks), `variables` for a `var:` source, null for a `cap:` one, which `DEVICE_WRITES` covers (the browser key's device control). Realtime: the mount follows `values:state` for its capability and `variables:state` for its variable; refetches every 5 min and when the page becomes visible.
- **The trigger** `keypad_tapped` (the user's request, 2026-10-25): *A Keypad button was tapped by [[code]]*, `code` an autocomplete (`pressCodeItems()`: Anyone `anyone`, Anyone with a code `any`, then the codes); `pressMatches()` matches by id, else by name (a code removed and made again). Tokens `code` (the code's name, `''` without one), `button`, `keypad` (from the press's `button`/`title`, ≤ 100). Fired after a press that's `done` (`fire()`, not awaited; a failed trigger is logged and never fails the press). A Flow the button starts gets no tags (Homey's *This Flow is started* has none), so the README points to this card. `app.ts` `registerKeypadFlows()`.
- **A web dashboard's code** (the user's request, 2026-10-25): see `.claude/rules/web-dashboards.md` (`KeypadService.unlock()`).
- **The wrong-code trigger** `keypad_wrong_code` (the user's yes, 2026-10-25): *A wrong code was typed on a Keypad*, no argument; tokens `button`, `keypad` (the widget's title, or a web dashboard's name with no button, from `unlock()`), `locked` (this try locked it), `left` (tries left, 0 once locked). Fired for each code checked and wrong (`wrongCodes` went up), not for a try refused while locked or a wrong current code on the settings page (`fireWrong()`, not awaited).
- Not a Smart Stack page (the keypad grows the widget, not tried in a slide; `test/stack-service.test.ts`). Diagnostics' `keypad`: the number of codes, presses, wrong codes, lockouts, codes locked now, the last error; never names, codes or hashes.

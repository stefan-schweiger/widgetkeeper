# Thermostat Presets widget (`thermostat`)

- Three preset buttons for one device (the `device` autocomplete); `lib/ThermostatService.ts`.
- Per button: `bNPower` (keep/on/off) and the autocompletes `bNMode`, `bNTemp` and `bNExtra`, in that order, each item `{capabilityId, value}`, read from the device's `target_temperature` range and its settable enum capabilities. Titled as in *Widget settings* (wk-066): `Button 1: power`, then `  – Mode`, `  – Temperature`, `  – Fan or other setting` (`test/locales.test.ts` checks every language).
- **The controls panel** (wk-079, Thomas's brief: more than the temperature; his choices 2026-10-21: in place of the whole widget, every setting, a ✕): the header is a button with a chevron (the core's `onHeader`; only with `onApply`). `openPanel()` puts `.tw-open` on the root, which hides the header and the buttons, and builds `.tw-controls` in `widget.js`: a top row with the name (14 bold) and a CSS-drawn ✕ (32 px), then a row per settable capability (`controlCaps()`: `onoff` as Power `Off | On`, `target_temperature` as `− 21.5° +` by the cap's `step` (0.5 without) within `min`/`max`, the mode then the other enums; not `measure_temperature` or `setable: false`), each a 12/16 muted label over a 40 px control in the buttons' look (`.tw-btn.tw-seg`, so the mode's colours and Muted/Vivid apply). An enum with ≤ 4 values is segmented and sent at once; more, `‹ Level 3 ›` cycles. Steppers send 700 ms after the last tap (`STEP_DELAY`). Each change is one `onApply` value (`/apply`), shown as sent for 10 s or until `pushChange` reports it; a failure shakes the row, shows `applyFailed` for 8 s and goes back. ✕, Escape or 30 s untouched (`IDLE_CLOSE_MS`) close it; a persistent message closes it; it re-measures (`core.refreshHeight()`), so Homey, the stack and web dashboards grow with it. The rows are rebuilt only when the name or the settings change. `CapInfo` carries `setable`, `min`, `max` and `step` for it. `dev/thermostat-preview.html?open=p2,p3` opens the preview's panels. The showcase mounts it with a no-op `onApply`, so the renders show the chevron.
- `title` (text, after `device`; Variable Presets' setting and strings): shown in place of the device's name, trimmed; empty or missing keeps the name. `widget.js`'s `setState()` swaps `name` before the presets module sees it.
- **The value beside the name** (wk-078, forum #239: an aircon with Off/Cool/Heat presets showed no temperature): the `sensor` autocomplete after `device` ("Value beside the name", flush left), Device Values' `listSlots()` (`None` first, then `Device · Capability`, id `<deviceId>:<capabilityId>`). Device Values tracks it: `/state` takes `&sensor=` and `thermostatState()` (`api.ts`) adds `app.values.getState([slot])`'s entry as `sensor: {deviceId, capabilityId, capability, value}`, left out when it can't be read (never failing the thermostat). The mount listens to `values:state` for that slot (`pushSensor()`). Shown with the kit's `formatValue()` through the presets module's `aside` hook, at the header's right end (`.tw-aside`, 17 bold, 14 in compact; kept whole while the name is cut).
- `GET /state?deviceId=` (re-read as the usual device widget: renames show, changed capabilities re-track, a device that can't be read is `{missing: true}`; any other failed refresh keeps the buttons with a transient error) and `POST /apply {deviceId, values}` (a button's tap adds `instance` and `button`, below). Realtime `thermostat:state`.
- **Flow cards** (the user's request, 2026-10-25; their choices: a button of a widget, not a preset typed into the card, plus the condition and the trigger): the action `thermostat_run_preset` "Run [[preset]]", the condition `thermostat_preset_active` "[[preset]] !{{is|isn't}} active" and the trigger `thermostat_preset_tapped` "[[preset]] was tapped" (tokens `device`, the device's name; `preset`, the button's text; `button`, 1–3). `lib/ThermostatPresetService.ts` (`app.thermostatPresets`, deps `{thermostat, stack, web, onTap}`); `app.ts` `registerThermostatFlows()`. Diagnostics' `thermostatPresets`: counts and the last error.
  - The `preset` argument (`listButtons()`): every button that sets something of every Thermostat Presets widget, Homey's dashboards (the Smart Stack's shared read, `StackService.dashboards()`, through the personal key; by name) then the web ones (while on), named `<title or device> · <button text>`, described `<dashboard> · Button n` (`<dashboard> (web)`). Id `<instance>:<n>`, `<instance>` being what that widget's `getWidgetInstanceId()` gives: the dashboard widget's id, or `web-<dashboardId>-<widgetId>`. Without a usable key, an item `none` at the end says Homey's buttons need one (`thermostat.keyItem`, the stack's `keyHint`/reason); the trigger's list starts with *Any button* (`{id: 'thermostat:any', any: true}`). Each item keeps `preset: {deviceId, values, modeCap}`.
  - Running and the condition read the widget's **current** settings (`resolve()`); while Homey's dashboards can't be read or the widget is gone, the item's saved `preset` (logged with debug, counted as `saved`). An emptied button or a widget without a device throws. `run()` turns the values into the device's (`deviceValues()`) and calls `thermostat.apply()`, so the order and waits are a tap's; `isActive()` is `presetMatches()` on `thermostat.getState()`.
  - The trigger: `presets.js` passes the button's index to the `apply` hook, `widget.js` gives `onApply` a second argument `{button}` (the panel's changes none), and `mount.js` adds `instance` (`getWidgetInstanceId()`; a Smart Stack page has the original's) and `button` to `/apply`. `api.ts` calls `tapped()` once `apply` resolved, not awaited; it fires with state `{id}`, matched by the run listener (`matches()`, or *Any button*), and never fails the tap. Taps from a web dashboard's `web-…` instance count for that widget's buttons.
  - `lib/thermostatPresets.ts` is the widget's device model copied to TS (`presetsFromSettings`, `widgetModeCap`/`modeCapOf` for `modeCap()`, `deviceValues`, `presetMatches`, `sameValue`, `presetLabel` for `presetText()` on one line); `test/thermostat-presets.test.ts` runs both on the same cases (lit, sent, text), so change them together.
  - Not yet tried on the Homey: whether a native widget's `getWidgetInstanceId()` is its dashboard widget id (only *Any button* would match otherwise), a run, and the trigger from a real tap.
- `apply` sets `onoff=true` first and `onoff=false` last, and sends mode → temperature → extra one at a time, waiting up to 4 s for each to be reported (some drivers check the fan speed against the *current* mode). It skips values the device has right then, updating its view after each confirmed value (aircons with a setpoint per mode bring back the mode's own setpoint).
- The **Mode** field defines the mode capability (often the driver's own, not `thermostat_mode`). Without `onoff`, "turn off" becomes that mode's `off` value and "turn on" is dropped (`deviceValues()` in the widget).
- A button is highlighted while the device matches every value it sets; a preset that doesn't turn the device off never matches while it's off. Without a match, the header shows `Currently Cool 23° · Fan auto` under the name. With one whose lit presets set no temperature (Arie's Off/Cool/Heat, wk-079), `Set to 21°` (`setpointText()`, the core's `lit` hook; not while off).
- Layout: a header with the device icon and name, then a segmented row of three buttons whose text comes from the preset (`21°` / `Heat` / `Fan slow`, or `Off`; no custom labels or icons). The name and values are 17 bold; the mode/extra text 12/16, a deliberate exception so three lines fit the 68 px buttons.
- `layout` (`standard`; `compact` adds `.tw-compact`, CSS only on the same markup, about 108 px with the frame against 156): a one-line header (`· Currently …` ellipsized beside the name, `.has-sub`; an error wraps below) and one-line buttons with the value and the mode, or the first extra without a mode (`.tw-modetext ~ .tw-extra` hides the rest, so presets that differ only in fan speed read the same).
- Dark mode: `body.tw-frame` mimics Homey's native device tiles (gated on `.homey-dark-mode`; light mode keeps the default frame): a `#181920` fill and a 1 px rim, lighter at the top (a fixed `::after`, out of the height), with a 10 px radius measured from a phone screenshot. Other widgets' dark frames copy it.
- **The shared presets module** (wk-068, for Variable Presets; Charts' pattern) is `public/presets.js` + `presets.css`, `window.WidgetkeeperPresets.create(root, hooks)`: the header (icon, name, subtitle), the segmented row (`--tw-count` columns), which button is lit (10 s optimistic after a tap, then `matches`), the shake and the messages (transient 8 s; persistent ones clear the state), the height. The hooks are `text(preset, state)` → `{big, mode, kind, extras}`, `matches`, `usable` (else disabled), `apply`, `failed(err)`, `current(state, presets)` (the subtitle while nothing is lit), `lit(state, active)` (while something is), `onHeader` + `headerLabel` (the header as a button with `.tw-chevron`, only once there's a state; neither exists without the hook), `refreshHeight()` (for a widget's own content), `aside(state)` (a value at the header's right end; the element only exists with the hook, so Variable Presets' markup is unchanged), plus `layout`, `onHeight` and `fallbackIcon: false` (no icon box without an icon). `presets.css` has everything but the mode colours (`[data-kind]` in the thermostat's `widget.css`), the `tw-` classes kept, so the thermostat's screenshot and previews stayed byte-identical. `widget.js` keeps the device model and text and reads `core.getState()`/`core.presets()`. Both `index.html`s, the dev pages that mount either, `DEPS` in `test/helpers/loadWidget.ts` and in the stack's `mount.js` load it first; the frame check reads `presets.css`, the rim check every `.css`.
- Device icons (`lib/deviceIcon.ts`, used by every device widget): fetched by the app, sent as an SVG data URL and used as a CSS mask (a rounded square as fallback). A user-picked icon (`device.iconOverride`, e.g. `lock`) is `https://my.homey.app/img/devices/<name>.svg` (public; the web app loads it from there), else the driver's `api.baseUrl` + `device.iconObj.url`. Each URL is fetched once per app run (it took 150–450 ms per widget load); a fetch gives up after 5 s, and a failed URL fails at once for 10 min (logged once).
- Colour style (`colorStyle`, Muted/Vivid; CLAUDE.md *Widget styling*, `kit.css`): after `layout`. The lit button (`presets.css`): Muted `--tw-shade`, solid, with white text (heat the orange shade, cool blue-600, auto green-700, dry and fan their colour mixed 70 % with black; Off keeps its grey); Vivid the bright colour as before 2026-10-18, the gradient. The user swapped them (round 2): the bright button looked like the stronger one.

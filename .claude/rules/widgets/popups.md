# Popups (widget `popups`, Flow cards `popup_*`)

- wk-084 (Drako74, community post #250): a Flow shows a message for a while, or asks Yes/No and gets the answer back as tags. The user's brief (2026-10-22): also on Homey's own dashboards, through a hidden widget that calls `Homey.popup()`, addressed **by a name on the widget**; pictures from **image tags, a live camera or an address**; the Ask card an **action card with tags**. Built on the branch `popups` (off `v1.1.0`, to merge into it).
- `lib/PopupService.ts` (`app.popups`, `new PopupService(homey, {cameras, web}, log, debug)`): popups in memory only, `{id, token, target, kind: message|ask, text (≤ 500), picture, sound, createdAt, until}`, at most 20 (the oldest closes, `replaced`). Targets: `all`, `web:<dashboardId>` (no longer offered, but a card saved with one still works; a deleted one throws `Dashboard not found`), `name:<key>` (`screenKey()`: trimmed, lower-cased, `Screen` when empty; the widget's `popupsScreenKey()` is the same). `show()` 1 s … 24 h; `ask()` 5 s … `MAX_ASK_SECONDS` and resolves `{answer, answered}`: the first answer from any screen wins (`answerFromSession(id, yes)` for a web dashboard, `answerWithToken(id, yes, token)` for the prompt page; likewise `imageFromSession()`/`imageWithToken()`, so a missing token is never a way in), a timeout, `close(target)` (everywhere closes all) or `stop()` is `{false, false}`. A later answer gets `{ok: false, reason: 'closed', answer}`; a message `notAsk`. Closed popups are remembered 10 min (≤ 50) so the prompt page can say how one ended.
- Realtime `popups:show {…view, now}` (no image bytes, **no token**) and `popups:close {id, answer|null, reason: answered|expired|replaced|closed}`. `until` is Homey's clock; screens move it into theirs with `now`, like the Smart Stack.
- Pictures: `{source: 'camera', deviceId}` is read through `CameraService.getSnapshot()` on every request (its 2 s reuse); an image tag (`args.droptoken`, an SDK `Image`: `getStream()` gives the bytes with `contentType`; a Reolink snapshot was a 1.3 MB JPEG, 2026-10-22) or an address (http/https, fetched by the Homey with a 10 s timeout, `image/*` only) is read once, ≤ 3 MB, kept as base64 with the popup (all open popups' stored pictures together ≤ 16 MB of base64, `MAX_PICTURES_TOTAL`: past it the oldest popups with one close as `replaced`, so 20 popups of 3 MB can't hold ~80 MB; Diagnostics' `popups.pictureSize`); the bytes are counted as they arrive (`readPicture()`), so a sender without (or with a wrong) `Content-Length` can't make the Homey read more. A picture that fails fails the Flow run with the reason.
- Flow cards (generated in 13 languages; their hints don't name the wait limit, so `MAX_ASK_SECONDS` can change alone, but the `seconds` arg's `max` must follow it): `popup_show` (text, screen, duration + seconds/minutes, `picture` autocomplete: *No picture*, the cameras (`cameraImage()`), or the address typed as `url:<address>`), `popup_ask` (question, screen, picture, seconds; tokens `answer`, `answered`), `popup_show_image`/`popup_ask_image` (`"droptoken": ["image", "string"]` in place of `picture`; a text tag is an address; separate cards because an autocomplete can't take tags), `popup_close`. The four Show and Ask cards end with `sound` (a dropdown: `none`, then `POPUP_SOUNDS` `chime`, `doorbell`, `alert`; the user's ask, 2026-10-24; `soundArg()` reads anything else, or a card saved before it, as none; tested equal to the kit's `sound.names` but Timers' `beep`). `screen` autocompletes `targetItems()`: Everywhere, the screen names seen (`popupNames` app setting, `{key: {name, seenAt}}`, ≤ 50, rewritten at most daily per name) with `Screen`, then the typed name. The web dashboards were in the list until the user took them out (2026-10-24): a web dashboard gets a name's popups through its Popups widget.
- **Tags from an action card only reach later cards in an Advanced Flow**: a standard Flow runs its THEN cards in parallel (seen on the Homey: two cards of one standard Flow started in the same millisecond, 2026-10-22). The Ask card's hint says so.
- The wait limit: **Homey ends an app's action card after 90 s** and runs its error output (measured 2026-10-22: an Advanced Flow Start → `popup_ask` asked to wait 300 s took the error path 90.0 s after the card started; one developer's forum report said ~60 s). So `MAX_ASK_SECONDS` is 85. To measure again: an Advanced Flow made through the API is only triggerable with a start card of `type: 'start'` (a `trigger` card with `homey:manager:flow:programmatic_trigger` gives `triggerable: false`), then `POST /api/manager/flow/advancedflow/<id>/trigger`; card keys must be UUIDs. Use one login for it (the CLI's `ApiCommandRuntime`, as `npm run test-dashboards` does): a few dozen `homey api raw` calls got `Too many requests` for about half an hour again.
- Sounds: the kit's `sound` (`play(name)`, `unlock()`, `names`; shared with Timers' beep, the user's ask, 2026-10-24), a few notes drawn with Web Audio (no sound files), played by the web dashboards page when a popup shows and by the prompt page when it opens (not on its polls), never by the widget itself. A browser refuses sound until the page has been used, and the in-app browser opens the prompt page without a tap, so **whether the phones play it is not yet tried**.
- Web dashboards: see `.claude/rules/web-dashboards.md` (*Popups*).
- The widget (`widgets/popups/`, transparent, manifest height 32): an empty row (`.pu-blank`, `min-height: 32px`; the user wanted it blank, 2026-10-24: it showed the kit's bell and the screen name before). It was invisible first: at 0 px, then 1 px, the iOS app kept its loading placeholder over it in and out of edit mode (2026-10-23), though popups opened. Its setting: `name` ("Screen name", text, default `Screen`). `mount.js` reads `GET /state?name=<as typed>` (`forScreen()`: its name's and everywhere's popups, and remembers the name) on load, every 5 min and on `visibilitychange`, and on a `popups:show` it would open (`wants()`: its screen's or everywhere's, still open, not opened here), as the event carries no token. **The token is only in `forScreen()`** (not in the realtime event, `all()`, `/web/setup` or `/web/popups`; the security audit, 2026-10-24): it alone answers through the public routes, and anyone who may listen to the app's realtime got it, past the web password and the screen names. Not yet tried on an iPhone: `Homey.popup()` after that request rather than straight from the event. Each popup still open opens once per device with `Homey.popup(<frame origin>/app/<appId>/settings/popup.html#id=&t=)` (the opened ids in `localStorage` `widgetkeeper.popups.opened`, ≤ 50, shared by every frame of the device). On a `web-…` instance it only calls `ready`: the page shows the popups for its name itself (`screenNamesOf()` in `settings/dashboard.js`). The web editor offers it (the user's ask, 2026-10-23, so one screen name reaches phones and a wall tablet's web dashboard alike; `web.about.popups`); `targetItems()` lists the web dashboards' Popups widgets' names too, as they never call `/state`. Not a Smart Stack page (`STACK_TYPES`).
- The prompt page (`settings/popup.html`, which loads the kit as `../widgets/spacer/kit.js` for its sounds, `popup.js`, `popup.css`; `prefers-color-scheme`, no Homey stylesheet): no login, so the app's routes `POST /popup/:id {t}`, `/popup/:id/image {t}`, `/popup/:id/answer {t, answer}` are **`"public": true`** (checked on the Homey 2026-10-22: a public route answers without a key at `http://<ip>/api/app/<appId>/…` and through `https://<homeyId>.connect.athom.com`; settings pages are served there without login too). The token (16 random bytes) is in the hash, never a query, sent in the body, compared with `timingSafeEqual`; a wrong one is `Not found`. They answer with web dashboards on or off. Its first call asks for the strings (`{t, strings: true}`); the polls every 2 s don't. It says *Answered: Yes*, *Answered on another screen*, *Time is up* (a question), *Closed* or *This popup is gone*, then *You can close this window* (it tries `window.close()`). Its `DEFAULT_STRINGS` equal en's `popups` (tested).
- Diagnostics' `popups`: the open ones' kind, target kind, picture source, sound and seconds left, the reasons recently closed, the screen names; never texts, addresses or tokens.
- `npm run test-dashboards [-- --native] popups`: a Popups widget named `Test` between two clocks.
- `dev/popups-preview.html`: the prompt page in three phone frames (a question with a drawn door, a message, answered elsewhere 4 s in). `dev/web-preview.html?popup=message|ask|picture|camera|elsewhere|named`: the web overlay (`named` goes to the screen name Hallway, which only the Hallway dashboard's Popups widget has).
- **On iOS** (the user, 2026-10-23): `Homey.popup()` from a realtime event opens the popup without a tap. It still does with the `/state` request in between (the event has no token since the security audit; the user, 2026-10-24). **Not yet tried**: Android, whether the 32 px row stops the loading placeholder on iOS, which origin a widget frame has on the phones (local or the relay), and whether the in-app browser lets the page close itself.
